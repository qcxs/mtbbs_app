# UA 设置 & 帖子列表解析

> 适用：处理 UA（移动/桌面）、帖子列表解析策略（ThreadListParserFactory）。按需。

## UA 控制

- **设置入口**：设置 → 站点与网络 → 浏览模式（移动版/桌面版）
- **默认值**：移动 UA（`Site.uaAndroid`）——`Site.effectiveUserAgent => userAgent.isNotEmpty ? userAgent : uaAndroid`；设置页把「移动版」标为默认推荐
- **存储位置**：`Site.userAgent`（空串表示用默认），持久化到 `Site.toJson`；读取统一走 `Site.effectiveUserAgent`（`SiteStore.instance.userAgent`）
- **生效范围**：导读/板块/搜索/我的帖子/用户空间 五个 HTTP 调用使用可配置 UA
- **其他所有 API** 强制使用桌面 UA（`Site.uaPc`），避免 DOM 解析与移动版 HTML 结构不匹配
- **`ApiService` 默认请求头** 固定为 `Site.uaPc`，所有未显式覆写的请求走此默认值

```
可配置 UA 的 API（5 个）：
  forumdisplay   → site.userAgent → 板块帖子列表
  guide          → site.userAgent → 导读
  search         → site.userAgent → 站内搜索（克米移动 ↔ 标准 Discuz）
  mythread       → site.userAgent → 我的帖子
  space          → site.userAgent → 用户空间（克米移动 ↔ 标准 PC，parse 层按 DOM 分流）

强制 PC UA 的 API（其余所有）：
  viewthread, viewpid, editor, ranklist, online, favorite,
  misc, mypost, 以及 ApiService 全局默认请求头 → Site.uaPc
```

- **帖子提醒（mypost）无 UA 覆写**：`lib/api/home/mypost/http.dart` 直接走 `ApiService` 默认请求头（桌面 UA），不读取站点 UA

- `mobile=2` 查询参数已全部移除，无需在 URL 中显式声明
  （注意：**`{前缀}_mobile` Cookie 是另一回事**，它优先级高于 UA，见下文）
- 52pojie 对 UA 不敏感，始终返回 PC 表格
- MT 论坛对 UA 敏感：移动→克米卡片，PC→标准表格或克米混合
- **用户空间页同时支持两套模板**（`api/home/space/parse.dart` 按 DOM 分流）：
  - 移动 UA → **克米移动**：`body.pg_space` / `.comiis_space_info`（含关注数/粉丝数/人气/Lv.x 等）
  - 桌面 UA → **标准 Discuz PC**：`#uhd` / `.u_profile` / `#pbbs` / `#psts`
  两套输出**统一字段**，页面按字段是否存在条件渲染（缺哪个不渲染哪个）。
- **用户空间支持页面级数据源覆盖**（避免被全局「浏览模式」一刀切）：空间页右上角菜单可单独选「跟随浏览模式 / 移动版 / 桌面版」，**仅本页生效并持久化**（设置项 `spaceSource`），不影响导读/板块等其它页面。实现：`api/home/space/http.dart` 的模块级 `_sourceOverride`（同 `_simulateBrowserHeaders` 模式，`SettingsProvider.load()` 注入）。

### 请求级覆盖（探针 / MCP 单次调用）

除"按站点持久化"的浏览模式外，还有一层**请求级覆盖**（`core/app/browse_mode.dart`），用于"某套模板解析出问题时换 UA 复测"：

- **探针**：加 `--dart-define=ua=mobile|desktop`（也接受 `m`/`pc`）；进程级、一次运行内所有请求固定用它。
- **MCP**：所有工具支持通用入参 `browse_mode=mobile|desktop`；Zone 级、**仅本次调用有效**（并发调用互不串味）。

覆盖生效时，`ApiService` 的拦截器会把它写进**每个请求**的 `User-Agent`（含本不设站点 UA 的接口）；优先级：请求级覆盖 > 空间页 `spaceSource` > 站点浏览模式。缺省/非法值 = 不覆盖（保持原行为）。

**白名单原则（只有少数接口支持移动端）**——支持移动端的接口必定同时支持 PC（有 PC 保底），故用**白名单**表达：

| | 接口 |
|---|---|
| 支持 `mobile` | 版块列表（forumdisplay）、导读（guide）、站内搜索（search）、我的帖子（mythread）、用户空间（space）；探针额外含 `debug.http` |
| 仅 `desktop`（PC-only） | 其余全部（帖子详情 / 排行 / 在线 / 小黑屋 / 圈子 / 积分 / 留言板 / 提醒 / 私信 / 收藏 / 好友 / 关注 / 写操作…） |

对白名单外的接口传 `mobile` 会被**明确拒绝**并提示改用 `desktop` 或省略 —— 避免"按移动 UA 请求 → 拿移动模板解析出错误数据"被 AI 当成正常结果、误以为两套模板等价。该白名单由单测锁定（`test/browse_mode_test.dart`）并与本篇 / docs/10 / docs/17 保持一致。

## 站点侧「浏览方式」Cookie —— 优先级高于 UA

**决策优先级**：`?mobile=` 参数／`{前缀}_mobile` Cookie **高于** UA 嗅探。
UA 只在两者都不存在时才参与决策 —— 也就是说，**UA 是可以被站点的一条 Cookie 完全压掉的**。

站点遇到"该页面无手机版"时，会渲染一段提示：

```html
您访问的页面无手机页面，是否进一步访问电脑版？
<a href="/k_misign-misc.html?operation=rewardrule&mobile=no">继续访问</a>
```

点「继续访问」（URL 带 `&mobile=no`）后站点下发：

```
Set-Cookie: {前缀}_mobile=no; Max-Age=3600; path=/; secure
```

实测（**同一手机 UA、同一 URL**，只差罐里有没有这条 Cookie）：

| 罐内 `*_mobile` | 导读页 bodyLength | 实际模板 |
|---|---|---|
| 无 | 173.5 KB | 克米移动卡片（`li.forumlist_li.comiis_znalist`） |
| 有 | 89.0 KB | `<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN"` → PC 表格 |

**为什么症状很"怪"**（排查时别被带偏）：

- **重新登录没用**：登录只新增认证 Cookie，不会清掉它；且 `Max-Age` 会被反复续期
  → 表现为「移动版」设置**永久失效**。
- **换一个账号就正常**：CookieJar 按账号隔离（`cookies/{host}/{账号}/`），
  只有中招的那个罐里有它。
- **和站点配置无关**：`Site.userAgent` 查过仍是移动 UA，别去怀疑设置项。

**App 的应对**：`ApiService._dropBrowseModeCookie()` 按后缀 `_mobile` 把该条从
**请求头**里摘掉（前缀可配置，故不写死全名），必须排在 `CookieManager` **之后** ——
后者才是把罐里 Cookie 合成 `cookie` 头的那一步，排在它前面时头上还什么都没有。
只改请求、不删罐里的数据（`cookie_jar` 4.0.9 也没有按名删除的接口）。

理由：App 的「浏览模式」是**用户显式设置**，不该被一条历史遗留的服务端偏好悄悄覆盖。
副作用仅限"该端点不再跟随站点记忆的浏览方式"，而这正是我们要的语义。

## 解析策略模式

入口 `parseThreadList(html)` → `ThreadListParserFactory.parse(html)`

工厂自动检测顺序：

| 优先级 | 解析器 | 特征 | 场景 |
|--------|--------|------|------|
| 1 | ComiisCardParser | `li.forumlist_li.comiis_znalist` | MT 移动 |
| 2 | DiscuzTableParser | `#threadlist th.common` | 52pj + MT PC 导读 |
| 3 | ComiisTableParser | `div.comiis_postlist` | MT PC 板块 |
| 4 | SpaceThreadParser | `table tr.th td.icn` | 我的帖子（MT/52pj） |

所有解析器输出统一的 `ThreadItem`，渲染层 `ThreadCard` 只认此模型。

### 帖子标记（精华等）解析

`ThreadItem.digest`（`>0` = 精华帖；渲染层在标题前加金色「精」徽标）。**各模板的标记位置不同，且并非每套都渲染**：

| 模板 | 精华标记 | 同处可见的其它标记 |
|---|---|---|
| 标准 Discuz PC（DiscuzTableParser） | 标题列 `span.tbox.tdigest`（文本「精华 N」） | 标题列 `span.trecic`（推荐）/`theatlevel`（热度）；`td.icn` 的 `i.tpin{1..4}`（置顶）、`i.fico-lock/vote/cart/reward/group/vs`（关闭/投票/商品/悬赏/活动/辩论）、`i.fico-image/fico-attachment`（图/附件） |
| 克米移动卡片（ComiisCardParser） | 标题链接内的前置 `<span class="bg_c f_f">精</span>` | `<span title="荐 N">荐</span>`（推荐）、`<span title="热度: N"><i class="kmhotico">`（热度） |
| 克米 PC 表格（ComiisTableParser） | `span.tbox.tdigest`（个别变体；见下） | 标题处 `<img>`：`alt=recommend`(推荐)/`heatlevel`(热度)/`attach_img`(图片附件)/`attachment`(附件)/`agree`(加分)、`{NNN}.small.gif`(印章) |
| 标准 Discuz 搜索（DiscuzSearchParser） | 无 | 搜索结果 `li.pbw` 结构里不含任何标记 |

- **克米 PC 不渲染精华**：MT 的克米 PC 列表实测**不输出**精华徽标（`filter=digest` 之外也不输出，含已知精华帖；其 `td.icn`/标题处均无 digest 痕迹），故 MT PC 端无法从列表区分精华——解析器仍保留 `tdigest` 探测以兼容其它站点/变体。
- **精华列表里徽标被服务端抑制**：`forumdisplay_list.htm` 的精华徽标带 `$filter != 'digest'` 条件，故"精华列表内解析不到 digest"属正常。
- 识别工具：`core/app/thread_parsers/parser_utils.dart` 的 `parseDigestBadge(scope)`（查 `.tdigest`）与 `hasDigestBadge(titleLink)`（查标题链接内「精」span）。回归用例见 `test/thread_parser_test.dart` 的「精华标记（digest）解析」组。
- 查"全部精华帖"走搜索 `srchfilter=digest`（见 `docs/18`）——导读 `view=digest` 只聚合最近 N 天，且其列表会抑制徽标。
