# 可选能力与平台降级

> 适用：新增依赖插件的功能、适配新平台（尤其鸿蒙）、排查“某平台入口消失 / 不可用”。
> 相关：`docs/01` 图片缓存与 Referer、`docs/02` 开发规范、`docs/20` 人机验证。

## 为什么需要这一层

Discuz 客户端的很多能力依赖原生插件（WebView、文件选择、相册、JS 引擎…）。
pub.dev 插件并非每个平台都有实现；鸿蒙尤其明显。问题分两种：

| 阶段 | 现象 | 处理 |
|---|---|---|
| 编译期 | 依赖被从 `pubspec.yaml` 移除，`import` 直接失败 | 只允许适配器 import 可选插件；必要时整文件替换为 stub |
| 运行时 | 依赖在、但平台没有原生实现，调用抛 `MissingPluginException` / `UnimplementedError` | 适配器捕获并 `AppCapabilities.disable()`，入口隐藏/降级 |

因此业务代码**不直接问插件是否可用**，只问能力注册表。

## 能力清单

实现：`lib/core/app/app_capabilities.dart`。

| 能力 | 依赖 | 默认可用 | 不可用时 |
|---|---|---|---|
| `webView` | `flutter_inappwebview` | 全平台 | 登录入口提示；内置浏览器/验证页不可用 |
| `filePicker` | `file_picker` | 全平台 | 选图/附件/导入 Markdown 返回 null（按取消处理） |
| `saveImage` | `gal` + `file_picker.saveFile` | 全平台 | 相册失败自动回退“另存为”；都失败则隐藏“生成图片” |
| `localJsSolver` | `flutter_qjs_next` | 非鸿蒙 | ACW 自解改用纯 Dart 算法，不影响体验 |
| `openExternalUrl` | `url_launcher` | 全平台 | 打不开浏览器时复制下载/发布页链接并提示 |
| `mcpServer` | `mcp_dart` | 全平台 | MCP 启动失败时关闭入口，不阻塞 App |

平台判定用 `AppCapabilities.isOhos`：比较 `defaultTargetPlatform.name` /
`Platform.operatingSystem` 字符串。**不要引用 `TargetPlatform.ohos`**——主线用官方
Flutter 编译时没有该枚举，会直接编译失败。

## 适配器边界

可选插件的 import 必须收敛在 `lib/platform/optional/`：

| 文件 | 职责 |
|---|---|
| `js_engine.dart` | 唯一 import `flutter_qjs_next`；执行失败即关闭 `localJsSolver` |
| `image_save.dart` | 唯一 import `gal` + `file_picker.saveFile`；相册 → 另存为回退 |
| `file_pick.dart` | 唯一 import `FilePicker.pickFiles` / `pickFile`；re-export `FileType`、`PlatformFile` |
| `file_save.dart` | 唯一 import `file_picker.saveFile`（非图片）；全平台传 bytes 由插件落盘（见下方差异） |
| `webview_support.dart` | 清 WebView 缓存/Cookie；唯一非 UI 的 `flutter_inappwebview` import |
| `external_url.dart` | 更新下载 / Release 页统一打开外部链接；失败即关闭 `openExternalUrl` |

**例外**：WebView 页面组件本身必须 import `flutter_inappwebview`（`auth/pages`、
`pages/browser`、`pages/verify`、`core/app/cookie_sync.dart`）。这些入口由
`AppCapabilities.webView` 在上层门控。

新增可选能力时：

1. `AppCapability` 加枚举 + `_defaultAvailable` 给平台默认值；
2. 在 `lib/platform/optional/` 新建适配器（业务代码只 import 它）；
3. 入口用 `AppCapabilities.isAvailable(...)` 包裹；
4. 运行时异常在适配器里 `disable`，不要让异常冒到 UI；
5. 补 `test/app_capabilities_test.dart` 的覆盖；
6. 更新本文件与 `AGENTS.md` 路由表；
7. 鸿蒙仓库 merge 后跑一次 `flutter analyze lib`。

## 平台差异检查清单（设计功能前先过一遍）

> 这是**提醒**，不是硬性验收标准：只要功能命中下面任一维度，就先问一句
> “Android / Windows / 鸿蒙分别会怎样”，再决定实现或降级方案。具体取舍由
> 开发者判断；本文只负责把已知的坑摆出来。

| 维度 | 先确认什么 |
|---|---|
| 文件选择 / 保存 | 插件是否要求 `bytes`？返回的是真实路径还是展示路径？选中的目录是否可写？是否需要清理插件复制的缓存副本？ |
| 权限 | 相册、通知等是否需要在运行时申请？被拒绝后的行为与提示是什么？ |
| 系统版本 | scoped storage、前台服务类型/时限、通知权限、预测性返回等是否随 API 级别变化？ |
| 路径 | 是否用 `package:path` 处理分隔符？有没有假设 `/`？ |
| 网络 | 目标平台是否允许明文 HTTP？证书校验策略是否一致？ |
| WebView / Cookie | CookieManager 的方法各端是否实现？是按 URL 过滤还是全量？ |
| 剪贴板 | 读写是否可能失败或被系统限制？失败时是否仍提示成功？ |
| 进程 / 生命周期 | 通知、前台服务、窗口关闭拦截在进程被杀/划掉/后台时是否收尾？ |
| 外部应用 | `url_launcher` / 文件打开是否有当前平台实现？失败是否有复制链接等降级？ |

已知差异（实现时直接对照）：

- **`file_picker.saveFile`（13.x）**：所有平台都**必须传 `bytes`**，由插件写入用户
  选中的位置并返回 `Uri?`（取消为 null）；桌面端不再“只返回路径、自己写盘”，
  **不要再 `File(path).write` 写第二次**。`type` / `allowedExtensions` 已弃用，
  扩展名取自 `fileName`。适配器见 `lib/platform/optional/file_save.dart` /
  `image_save.dart`；鸿蒙分支的 `initialDirectory` 语义见 docs/07 #117。
- **scoped storage**：`getDirectoryPath` 返回的是从 SAF 树 URI 反推的文件系统
  路径，Android 11+ 应用没有直接写权限。需要写目录时走 SAF 输出流，或改用
  `saveFile(bytes:)`。
- **file_picker 选文件**：Android/iOS 会把文件复制到 `{cache}/file_picker/...`，
  读完/上传后要 `FilePick.cleanupTemp(path)`，否则缓存持续膨胀（桌面端直接返回
  原路径，无需清理）。
- **相册（gal）**：Android API ≤28 需要运行时 `WRITE_EXTERNAL_STORAGE`；API 29
  保存到默认图库不需要权限（保存到自定义 album 才需要
  `requestLegacyExternalStorage`）；`name` 不要带扩展名。
- **明文 HTTP**：Android 的 `network_security_config.xml` 默认只放行回环地址，
  用户添加 `http://` 站点后所有请求会被系统拦截；Windows 不受此限制。站点入口
  已提前拒绝（`site_management.dart`）。
- **WebView Cookie**：`getAllCookies()` 在 Windows 未实现；统一用
  `getCookies(url:)`（按 URL 过滤，Android 缺 `GET_COOKIE_INFO` 时也没有
  domain）。`useShouldOverrideUrlLoading` 在 flutter_inappwebview 6.x 会按回调
  自动推断，不必手动设。
- **剪贴板**：`Clipboard.setData` 可能失败（平台限制/被占用），写入必须 `await`
  并检查结果，不能先提示“已复制”（docs/07 #107）。
- **插件缺失**：同时捕获 `MissingPluginException`（`Exception`）与
  `UnimplementedError`（`Error`）；只写 `on Error` 会漏掉前者。
- **通知 / 前台服务**：Android 13+ 需要 `POST_NOTIFICATIONS`；Android 14+ 前台
  服务要声明类型与权限；Android 15+ `dataSync` 有 6 小时/24 小时配额，必须实现
  `Service.onTimeout` 主动停止。
- **路径分隔符**：Windows 用 `\`，不要用 `split('/')` 取文件名，统一
  `package:path` 的 `basename()`。
- **返回键 / 深链**：Android 16+ 预测性返回需显式
  `enableOnBackInvokedCallback=false`；自定义深链要关掉 Flutter 自带处理
  （见 docs/07 #64）。
- **Windows 证书**：`main.dart` 目前用 `HttpOverrides` 放宽了 Windows 的证书
  校验（历史兼容）。涉及证书/网络安全的功能不要假设各平台一致，需单独评估。

## ACW 自解的双路径

人机验证必须“无感”，因此不能因为某个平台没有 JS 引擎就退化为弹 WebView：

1. **QuickJS**（`flutter_qjs_next`）——执行页面真实脚本，能跟随站点改算法；
2. **纯 Dart 算法**（`lib/core/app/acw_pure_dart.dart`）——无 JS 引擎、脚本执行失败
   或拿不到结果时兜底。与探针 `tool/acw_challenge.dart` 共用同一份实现（后者只做
   re-export），避免两套算法漂移；
3. 两段都失败才返回 null，由 `VerificationGate` 走 WebView 人工验证。

改算法时只改 `acw_pure_dart.dart`；`JsChallengeSolver` 与探针会自动同步。

## 更新检查与外部链接

更新检查本身是纯 Dart（`http` + GitHub API），鸿蒙可直接复用；与平台相关的只有
“打开下载地址”这一步：

- 更新源与渠道**构建期注入**（`mtbbs.repo` / `mtbbs.channel`）。未注入的本地包
  不检查更新，关于页也不显示更新入口（见 `docs/15`「应用内更新检查」）；
- 下载 / Release 页统一走 `lib/platform/optional/external_url.dart`；鸿蒙若没有
  `url_launcher` 实现，适配器会关闭 `openExternalUrl`，弹窗降级为**复制链接**；
- App 不做应用内下载与安装：鸿蒙产物（`.hap`）由浏览器/应用市场接管，弹窗在
  找不到匹配产物时提供「打开发布页」兜底；
- 鸿蒙 CI 打包时传 `-Repo qcxs/mtbbs_app_ohos -Channel release`，无需修改 `lib/`。

## 鸿蒙仓库的边界

鸿蒙是**独立项目**（[mtbbs_app_ohos](https://github.com/qcxs/mtbbs_app_ohos)），与主线
只在 `lib/` 的"上游文件"上保持一致：

- 通过 `upstream` / 本地主线 remote 合并更新，冲突面应只有 `ohos/`、`docs/ohos/` 与
  `pubspec.yaml` 的 `dependency_overrides` 段；
- 鸿蒙专属 Dart 逻辑写在鸿蒙仓库的 `lib/ohos/**`（该目录主线永不存在 → 合并零冲突）；
  `lib/` 其余文件取主线，不散写鸿蒙分支。通用差异仍优先用上面的能力开关；
- 平台判定一律用 `defaultTargetPlatform.name` / `Platform.operatingSystem` 字符串，
  不要引用 `TargetPlatform.ohos`（主线用官方 Flutter 编译时没有该枚举）；
- 纯原生能力（通知、权限、窗口、系统 API）只写鸿蒙仓库的 `ohos/`，主线不新增平台分支；
- 依赖覆盖常驻在鸿蒙仓库 `pubspec.yaml` 的 `dependency_overrides` 段（不再是单独的
  `pubspec_overrides.yaml`）；上游升级被覆盖插件后，先确认 OH fork 分支再改 `ref`。

完整合并流程与文件归属矩阵见鸿蒙仓库 `docs/ohos/03-同步上游.md`。
