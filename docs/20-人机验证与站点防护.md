# 人机验证与站点防护

> 适用：请求"返回的不是论坛页"、App 弹出站点验证页、要处理 `acw_*` cookie，或准备改 `JsChallengeSolver` / `VerificationGate` / `looksLikeInterstitialPage` 时读。按需。

## 一句话

站点（MT 论坛）前置阿里云 ESA：未过挑战时返回 200 + 几 KB 的挑战页。App 用**内嵌 JS 引擎本地自解**后重放请求（用户无感）；解不出来（滑块 / 点选等交互式）才弹内置浏览器让人工完成。探针走同一条链路，另备一份纯 Dart 算法兜底。

## 一、站点侧机制

| 现象 | 实测值 |
|---|---|
| 响应头 | `server: ESA`、`x-tengine-error: denied by http_custom` |
| 挑战页 | `<html><script>var arg1='<40位hex>'…</script></html>`，约 4.3 KB |
| 同响应的 `Set-Cookie` | `acw_tc` + `cdn_sec_tc`（**两者同值**、`HttpOnly`、`Max-Age=3600`） |
| 页面 JS 写入 | `acw_sc__v2=<40位hex>`（`expires = now + 3600000ms`），随后 `location.reload()` |
| 放行后请求需带 | `acw_tc` + `cdn_sec_tc` + `acw_sc__v2`，三者缺一不可 |

**配对规则（最重要的约束）**：`acw_sc__v2` 必须等于"服务端**本轮**为同一 `acw_tc` 下发的 `arg1`"的函数值。于是

- 只能用**本次挑战响应**里的 `arg1` 来算（同一响应的 `Set-Cookie` 会给出配对的 `acw_tc`）；
- **把浏览器里复制出来的 `acw_sc__v2` 灌给 Dio 会被拦**——它对应的是浏览器那一轮的 `arg1`。别再沿用"复制 cookie 绕过"的老办法。

### 网宿 WZWS（52pojie）：跳转式挑战

| 现象 | 实测值 |
|---|---|
| 响应头 | `WZWS-RAY: 1229-…-w-waf08zzst`（没有 `server: ESA`） |
| 挑战页 | 约 36 KB 混淆脚本 + `<noscript>Please enable JavaScript…`，**无 `arg1`、无 `Set-Cookie`** |
| 页面 JS 动作 | 既不写 `document.cookie`、也不发 XHR，只 `window.location = "/WZWSREL<base64>?wzwschallenge=<标签>&wzwsinfos=<base64 JSON>"` |
| 服务端响应 | 该地址 302 回原路径；后续普通请求直接给真实页面，**不需要任何 cookie** |
| 关键参数 | `wzwschallenge` = `WZWS_CONFIRM_PREFIX_LABEL` + 字符和×乘数 + 常数；`wzwsinfos` = base64(`{hostname, scheme, verify}`) |

所以 L1 对它是"**执行脚本 → 捕获 `window.location` 赋值 → 用同一个 Dio 请求该地址**"，而不是读 cookie。地址来自页面脚本，只能用于**同 host**（`_solveJsChallengeLocally` 会校验 `target.host == base.host`）。实测完成跳转后连续请求全部放行，无需把任何 token 落盘。

> 该挑战只在**非浏览器 HTTP 指纹**（PowerShell / 原生 HttpClient 等）下出现；真实 Chrome 与 App 的常规请求都没有见过它。把它做成 L1 是**兜底**，不是常态路径。

## 二、怎么判定"被拦了"

`looksLikeInterstitialPage()`（`core/app/page_helper.dart`）**刻意不认厂商特征**，只判断"结构上不是一个能用的页面"：`content-type` 含 `text/html` + 正文含 `<html` + 体积 < 64 KB，且（无 `<body>` 但含 `<script>`/`<meta>`）或（有 `<body>` 但**没有** Discuz 骨架且可见文本 < 256 字）。骨架痕迹为 `discuz` / `formhash` / `comiis` / `id=ct|hd|ft|postlist|thread_subject`。

判定**宁可靠向"论坛页"**：误判会平白弹窗打扰用户，漏判只是回到既有的"页面结构可能已变更"提示。

## 三、App 的两级恢复

入口是 `ApiService._recoverFromInterstitial`：Dio 拦截器在 200 响应上判定命中后调用它，返回 true 表示"已恢复"，由调用方重放本次请求并打 `kInterstitialHandledFlag`（防递归）。

| 级别 | 实现 | 生效条件 | 用户感知 |
|---|---|---|---|
| **L1 本地自解** | `core/app/js_challenge_solver.dart` | 能从挑战页抠出 `<script>` 且引擎跑通 | **完全无感** |
| **L2 人工验证** | `core/app/verification_gate.dart` + `pages/verify/verify_browser_page.dart` | L1 失败：交互式验证 / 脚本结构变化 / 引擎不可用 | 全屏弹窗，手动完成 |

- **L1 执行的是挑战页里的真实脚本**（不是照抄算法），站点改算法我们不用改代码；代价是要处理脚本的反调试（见第四节）。脚本的两种收尾（写 cookie / 要求跳转）都由 L1 处理。
- **L2 不能删**：它既是交互式验证的唯一方案，也是算法变更时的兜底。
- **非 GET 只解不重放**：写操作重放有重复提交风险，解完让用户手动重试。
- **无 UI 上下文直接放弃**：`VerificationGate` 取不到 `Navigator`（后台任务、启动早期、MCP 服务端请求）就返回失败，绝不挂起等待——那些场景没有用户可弹。
- **不跨罐镜像 `acw_sc__v2`**：它与"本轮 arg1"绑定，复制到别的罐会与那边的 `acw_tc` 错配；其它罐下次被挑战时各自静默自解即可。
- 想**单独验证 L2**（平时被 L1 遮住）见第九节。

## 四、L1 的四个硬约束（改之前必看）

四条都在 `JsChallengeSolver` 里，改动务必保留：

1. **JS 栈上限必须调小到 256 KiB**。挑战脚本里的函数 `b()` 会**故意无限递归到栈溢出**、靠 `catch` 吞掉异常来区分原生/解释执行；用引擎默认的 1 MiB 时**原生线程栈先炸**——进程以 `0xC00000FD` 退出，Dart 侧没有任何异常和日志。
2. **必须显式传入栈上限，并启用超时/内存护栏**。`flutter_qjs_next` 全平台内置同一 QuickJS（无 Apple JSC 分叉），故一次 `getJavascriptRuntime(stackSize: 256KiB, timeout: 5000, memoryLimit: 32MiB)` 对全平台一致生效，**不需要按平台分支**。`timeout` 实测可中断同步 `evaluate` 的死循环（返回可捕获的 `InternalError: interrupted`），用于脚本变更后兜底。
3. **DOM 桩必须含 `document.location`，且 cookie 按名合并**（ACW 调 `document.location.reload()`；WZWS 多次写 cookie 的可能性不能排除——整串覆盖式 setter 会丢前面的值）。其余按最小集提供：`window`/`self`/`navigator`/`console`/`alert` 等；**不要注入任何 Dart 能力、不要开 fetch/xhr**。
4. **`setTimeout`/`setInterval` 必须存在但绝不执行回调**，同时 `window.location` / `document.location` 的**赋值要被捕获**。WZWS 用 `setInterval` 挂 `while(true)` 递归反调试（执行只会白耗 5 秒配额），而它的通行证正是 `window.location = "…?wzwschallenge=…"` 这一次跳转——桩里必须把它记下来交给 Dart 侧发起请求。

引擎与依赖的构建坑见 `docs/09` 的 `flutter_qjs_next` 行（旧 `flutter_js` 的 JitPack 依赖、Gradle 卡死、JVM target 冲突与 KGP 弃用警告，已随本次替换一并移除）。

## 五、探针

探针跑的是 App 的完整链路，因此挑战默认由 L1 解掉。但 `flutter test` 下加载原生库不方便，所以探针另备一份**纯 Dart 算法**（`tool/acw_challenge.dart`）作兜底，同时充当"算法是否已变"的哨兵——**两套实现对同一 `arg1` 必须给出相同结果**。命令、参数与日志判读见 `docs/10` 5.1。

## 六、观测结论：站点不会"短时间内反复验证"

用 Chrome（CDP）复现真实用户行为并逐次记录 `acw_sc__v2`：**11 次导航 / 约 4 分钟**（含 3 秒快节奏、6 秒人类节奏、45 秒空闲，另加 3 标签并发）**该值全程不变、0 次重验证**。据此：

- 浏览器的"无感"不是因为站点对它更宽松，而是它**在同一次加载里毫秒级静默重算**；
- App 侧"短时间内又要验证"的**来源是客户端不能自解**（每次 token 需要刷新时只能弹窗），不是站点风控节奏；
- 修好自解后实测：1 次自解落盘 → 后续 26 次连续/分散请求（含列表翻页、帖子详情）**0 次**再验证。

## 七、将来遇到交互式验证（滑块 / 点选 / 短信）

| 类型 | 判据 | 方案 |
|---|---|---|
| A 可计算、无交互 | 正文里有可解析的脚本或参数 | L1 本地自解（现成） |
| B 交互式 | 有滑块/图形/短信 DOM，或 L1 连续失败 | L2 弹 `VerifyBrowserPage`，用户完成后 cookie 回流 |
| C 纯指纹 / 行为拦截 | 连 cookie 都不下发（TLS/JA3 层拒绝） | cookie 与自解都无效：只能让该请求**真的从 WebView 发出**（`evaluateJavascript('fetch(…)')` 取回正文当 HTTP 客户端用），或降级为内置浏览器打开 |

C 类目前未出现，属预案。若 B 类成为常态，优先改造 `VerifyBrowserPage`：只在交互式时弹、别 `deleteAllCookies()` 清空全部、并延长失败冷却。

## 九、怎么单独验证 L2（WebView）是否可用

L1 平时会遮住 L2，所以有一个**开发者选项页**用于强制复现它：

- **入口**：关于页的**应用图标连续点击 7 次**解锁（相邻两次间隔 >2 秒则重新计数）；解锁后**单击图标**即进入；页底「关闭开发者选项」可隐藏入口（开关的值保留）。
- 打开页内开关「改用网页完成」后，`JsChallengeSolver.solve()` 直接返回 null，挑战必定落到 WebView。该页也是以后收纳这类"排障 / 诊断专用"开关的地方——新增项只改 `models/developer_settings.dart` 一个列表即可。

还要**制造一次挑战**，否则带着有效 token 不会被拦。三者任选：

- 设置 → 站点与账号 → **清空登录数据**（罐清空后首个请求必被挑战）；
- 换一个从未登录过的账号（新罐为空，首请求必被挑战）；
- 等 token 自然过期（约 1 小时，不推荐）。

然后进任意帖子触发请求，应弹出「站点验证」。**判定"web 可用"的唯一标准是"弹窗关闭后原请求被自动重放、能看到内容"**，而不是"页面上看起来验证过了"。

诊断日志（`flutter run` 控制台）：

| 日志 | 含义 |
|---|---|
| `[PAGE] 弹出人机验证：<url>` | L2 已触发 |
| `[PAGE] WebView → Dio 回流 <host>: N 条（新增 …）` | cookie 是否回流成功——「页面里过了、App 仍失败」的头号嫌疑就在这里 |
| `[PAGE] 人机验证结束：已通过 / 未通过` | 探测判据的最终结论 |
| `[DIO] <path> 已通过验证，重放请求` | 恢复成功 |

失败时优先核对三处：探测用的 `_probeUrl` 与 `SiteStore.baseUrl` 是否同 host（不同域会把 cookie 回流到错罐）、90 秒超时（`等待超时，请稍后重试`）、以及设置项「人机验证自动处理」是否被关（关着时 `VerificationGate.handle` 直接返回 false，根本不弹）。

## 十、排查速查

- **"验证过还是不行 / 时好时坏"** → 先排除"用了复制来的 cookie"（见第一节配对规则），再看日志里有没有 `已本地自解验证`。
- **"重启后才弹验证"** → cookie 落盘或归属问题，见 `docs/07 #73`。
- **"构建卡死、CPU 不转"** → 旧 `flutter_js` 时代的历史坑（Gradle 直连 Maven Central 断流），已随替换为 `flutter_qjs_next` 消失；若再现见 `docs/09`。
