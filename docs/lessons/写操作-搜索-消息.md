## 写操作 API

29. **Discuz 默认操作 API 直接拼接 URL，不要从 DOM 提取入口** — 点赞（`action=recommend`）、评分（`action=rate`）等 Discuz 自带操作，URL 是固定的通用格式：`forum.php?mod=misc&action=rate&tid={tid}&pid={pid}`（加 `&inajax=1` 取弹窗/响应），用页面已有的 tid/pid 直接拼即可。**不要**专门去帖子 DOM 里定位评分/点赞按钮再提取 onclick/href——按钮 DOM 位置随模板变化（标准 Discuz 在 `.po .pob.cl`，克米在第二个 `td.plc` 的 `#p_btn`）、onclick 里的路径可能带或不带前导斜杠，为每个模板适配提取逻辑纯属浪费时间，且"按钮取不到"会让整个功能不可用。**DOM 提取唯一必要场景是需要页面其他位置拿不到的参数（如收藏的 favid）；需要 formHash 时直接用页面全局 formhash**——一个页面所有表单共用一个，取任意 `<input name="formhash">` 即可，比定位特定功能的表单更通用。教训：评分功能曾大量时间耗在"评分按钮在第几个 td.plc、onclick 有没有前导 `/`"上，实际一行拼接 URL 就解决；入口对无权限/已评分的用户本就该由弹窗响应拦截（提示信息无 `<form>` → 抛 FormatException），不该靠"有没有按钮"来体现。

74. **搜索接口的 `inajax=1` 分支没有分页，必须走完整 HTML** — 现象：给 `search.php?mod=forum&srchtxt=…` 追加 `&inajax=1` 后，返回变成 `<root><![CDATA[…]]></root>` 包裹的**列表 HTML 片段**，既没有页面骨架也没有 `.pg` 分页栏（和导读的 AJAX 分支一样）。**根因**：Discuz 的 inajax 只输出模板片段，分页 `$multipage` 不在片段里；搜索靠 `searchid` 翻页，而 searchid 只出现在**重定向后的最终 URL** 上。**正解**：搜索一律走完整 HTML——`GET /search.php?mod=forum&srchtxt={kw}&searchsubmit=yes`，Dio 跟随 302 后从 `response.realUri` 取 `searchid`，后续翻页回传该 id；`submitcheck('searchsubmit',1)` 的 `$allowget=1` 会跳过 formhash 校验，所以**纯 GET、无需 formhash、无需 POST**。完整链路见 `docs/18-站内搜索.md`。

75. **同一套"错误/消息页"在移动端和 PC 端是两种结构，`prepareDoc` 只覆盖了一部分** — 现象：游客在 MT 搜索，接口既不报错也不像正常结果，客户端把"需要登录"当成了"没有找到结果"。**根因**：Discuz 的兜底页按模板分两套——PC 是消息页（`#main_message > #messagetext.alert_info`，title「提示信息」）；移动克米要么把消息渲染成 `div.comiis_password_top > p.f_c`（**限流**，如"抱歉，您在 10 秒内只能进行一次搜索"），要么直接 **302 到 comiis 登录页**（**游客无权**，title「登录」，且**没有** `input[name=loginsubmit]`，故 `checkPageError` 第 4 条不命中）。`checkPageError` 第 1 条只认 `comiis_password_top`，于是登录页这条漏网。**修法**：在搜索 `parse` 里补一层兜底——title 含「登录/提示信息」或命中 `body.pg_logging`/`#loginform`/`input[name=loginsubmit]` → 判为 `success:false`，`loginRequired` 看 `discuz_uid=0`；能取到的 `#messagetext` 文案原样带出。**教训**：判定"这不是一个正常的业务页"时，别只认一种模板的容器；`#messagetext`（PC）与 `comiis_password_top`（移动消息）/登录页 title（移动游客）是三个不同的信号，缺一个就会把错误态静默降级成"空结果"。频率限制的 UX 处理见 `docs/18-站内搜索.md`。

82. **`misc.php?mod=swfupload` 的响应格式由 `simple` 参数决定——不带 `simple` 时服务端只回一个"裸 aid"** — 症状：**附件上传永远失败**（图片正常），抛"上传失败"且 `code` 为空。**根因**（读 `source/class/forum/forum_upload.php`）：响应体分三个分支——`simple=1` → `DISCUZUPLOAD|{statusid}|{aid}|…`；`simple=2` → `DISCUZUPLOAD|{type}|{statusid}|{aid}|{isimage}|{file}|{name}|{err}`；**两者都没带** → `echo $statusid ? -$statusid : $this->aid;`，即只回一个**裸 aid**。App 的 `uploadImage` 带了 `simple=2`（解析 `|` 分段），而 `uploadAttachment` 漏了它，于是拿到 `"49"` 这种两字符响应，`parts[2] == '0'` 永远不成立。**修法**：附件上传 URL 同样加 `&simple=2`（解析器本就能处理：`parts[2]`=statusid、`parts[3]`=aid、`parts[6]`=文件名）。**教训**：① 同一站点、同类端点，参数少一个就换了一套响应格式——**照抄图片那条成功路径的参数**比重新推演快；② "裸 aid / 裸数字"这种极短响应是最容易被静默吞掉的失败态（`parts.length` 不足时 App 只报"上传失败"、`code=?`），排查时先看**响应原文长度**。实测脚本：`tool/` 下一次性的 attachnew 探针（带 `simple=2` 后 `uploadAttachment` 立即 `success=true`）。相关：附件必须进 `attachnew` 才会绑定到帖子，见 `docs/12` §1。

95. **`succeedhandle_` 的 redirect 不一定是查询串式 URL，tid/pid 可能只在第 3 参 JS 对象或伪静态路径里** — 症状：MT 论坛发帖成功（返回 `非常感谢，您的主题已发布…`）却**不跳转新帖**，走了"打开我的帖子"的保底；测试站点正常。**根因**：MT 回的是伪静态 URL `thread-174520-1-1.html`（不含 `tid=`），而 `parseSubmitResponse` 只认 `RegExp(r'tid=(\d+)')`；实则 tid/pid 同时出现在 ① `succeedhandle_(redirect, message, {params})` 的第 3 参 **JS 对象**（`{'fid':'42','tid':'174520','pid':'11947117',…}`）与 ② 伪静态路径 `thread-{tid}-{page}-{ordertype}.html` 里。**修法**（`core/parser/xml_helper.dart` 的 `parseSubmitResponse`）：正则补捕获第 3 参对象；tid/pid **各自**按"可靠性递减"链式提取——第 3 参对象 → 查询串（tid：`tid=`/`ptid=`；pid：`pid=`/`#pid`）→ 伪静态 `thread-(\d+)`；两字段独立取值，避免"对象里只有 pid、URL 里只有 tid"时相互拖累。**教训**：Discuz 的 `redirect` 参数**可能被伪静态重写**，不要假设它一定带 `tid=`；`succeedhandle_` 的第 3 参是**结构化字段**（与站点 URL 风格无关），遇到"某字段取不到"先去那里找。回归测试：`test/submit_response_test.dart`。

## 外部搜索（Bing）

77. **直连 Bing `?q=` 会丢 `site:`，必须带搜索框表单参数 `form=QBRE`** — 现象：App 的 Bing 搜索（`pages/search/search_page.dart` 拼 URL 用内置浏览器打开）"结果不准"——明明带了 `site:{域名}`，却返回 mt.cc / jb51.net / 百度百科等**全网**结果。**根因**：Bing 用 `form=` 参数区分"用户从搜索框提交"；直连 `https://www.bing.com/search?q=<query> site:<domain>` 缺该参数时，Bing 把请求当作**外部跳转**改写查询（响应最终 URL 被追加 `rdr=1&rdrig=<guid>`），`site:` 被静默丢弃。**实测（cn.bing.com，移动 UA）**：`q=MT管理器 site:bbs.binmt.cc` → 10 条全在站外（`rdr=1`）；同 URL 加 `&form=QBRE` → **10/10 全在 bbs.binmt.cc**。非品牌词（`脱壳 site:`、`逆向 site:`）不受影响，**品牌/实体词必现**（`MT管理器`、`MT论坛` 均复现）。**逆向方式**：Bing 结果页 `<form id="sb_form" action="/search" method="get">`，字段 `q` + 隐藏 `qs=ds`、`form=QBRE`（`qs` 非必需，`form=QBRE` 单独即生效）。**修复**：URL 追加 `&form=QBRE`。**注意**：空格编成 `%20`（`Uri.encodeComponent`）还是 `+`（`Uri.encodeQueryComponent` / 浏览器表单）**都失败**——与空格转码无关，别被"空格应该是 `+`"带偏（两者实测同样丢 `site:`）。

## 消息与提醒（do=notice）

94. **提醒页有三个反直觉行为：只置"你实际打开的那个子类型"为已读、默认子类型由服务端挑、不在 `notice_structure` 里的 view/type 会被静默降级** — 症状：我的帖子显示 1 条未读，点进去看到的是「帖子」子类型（里面没有新东西），徽标仍挂着 1，下次探测还在；MT 上「管理工作」点进去看到的却是**普通帖子提醒**；「评分」和「帖子」拿回**同一批数据**。**根因**（`source/include/space/space_notice.php`）：① `$newnotify` 仅在**本次查询到的**条目里有 `new=1` 时才 `ignore()` + `update_newprompt()` —— 打开「帖子」而新消息在「点评」时，**服务端什么都没置已读**，客户端若"乐观整组清零"就与真实状态不一致（先清空、下次探测又冒出来）。② `$deftype` 会遍历 `notice_structure` 取**第一个 `newprompt_num` 非 0 的子类型**，所以**不传 `type` 时服务端就返回有未读的那个**；客户端硬传 `type=post` 恰好把它跳过。③ 非管理员的 `manage` 在该文件开头被 `unset`，`view=manage` 不合法 → `$view='all'` → 返回**全部提醒**（看着像帖子）；`type` 同理，不在 `notice_structure` 里就**静默回退**默认子类型（拿回别人的数据）。**修法**（`core/parser/notice_segments.dart` 的 `parseNoticeNav` + `core/app/notice_nav_store.dart` + `notice_badge.dart`）：① 首次请求**不带 `type`**，从返回页面子类型栏的 `li.a` 反推站点实际打开的子类型（用户手动点过之后不再被覆盖）；② 计数改成**数据驱动**（页面侧栏给组级、子栏给子类型级；注意它们都是**读前**的值，见下方"补（计数模型）"），读完的子类型立刻清零，不再本地瞎猜；③ Tab 与子类型 chip 一律按页面侧栏/子栏裁剪（站点没有 `manage`、没有 `rate` 就不显示）。**教训**：Discuz 的"打开即已读"是**按被查询的子集**生效的，凡是想"打开分组就当作读完"的乐观更新都要先问一句"服务端到底置已读了哪些"；跨页面的**权威计数往往就在页面自己身上**（侧栏/子栏的 `(N)`），比另发一次探测请求既准又省。相关：非破坏性探测（只读 header，绝不请求 `do=notice` 以免误置已读）见 `core/app/notice_badge.dart`。**补（计数模型）**：提醒页面渲染的组计数是**读前**的——Discuz 每个请求开头才算一次 `newprompt`，而同一次请求里是先 `ignore()` 再渲染模板，所以拿页面侧栏去覆盖徽标本身就滞后一拍。正解是**数据驱动**：页面的子栏给出各子类型计数 → 分组未读 = 各子类型之和（`category_num[view]` 本就是该视图各 `newprompt_num[type]` 之和），读完某个子类型就把它清零，分组立刻跟着降，不必等下一次探测（否则会出现"点评已读完、我的帖子还挂着 1"这种反直觉状态）。但子类型数据会过期（新消息到达后它不再为真），因此探测（header，是**探测那一刻**的权威值）回来的组计数一旦与"子类型之和"对不上，就丢弃该视图的子类型数据、回落到探测值兜底（`NoticeBadgeController._dropStaleSubtypeCounts`）。

93. **会"重建"的 `TabController` 必须用 `TickerProviderStateMixin`，且长度要在 `build` 里跟 Tab 列表对齐** — 症状：消息页从「我的消息」切到「我的帖子」直接抛 `_MessagePageState is a SingleTickerProviderStateMixin but multiple tickers were created`，紧接着 `Controller's length property (6) does not match the number of tabs (5)`。**根因**：① 视图集合会变（各分组页把各自的页面导航同步进 `NoticeNavStore`，站点侧可能是 5/6 交替），原实现**在通知回调里**按"当前长度"新建 `TabController` —— `SingleTickerProviderStateMixin` 只允许创建**一个** ticker，第二次直接断言失败；② 新长度在回调里算，与随后 `build` 实际用的 Tab 列表可能脱节 → TabBar/TabBarView 长度不匹配。**修法**（`pages/message/message_page.dart`）：① 改用 `TickerProviderStateMixin`；② TabController 的**长度对齐统一放进 `build`**（`_syncTabController(tabs.length)`：长度变了才重建、旧控制器帧末 dispose、`index` clamp），通知回调只 `setState`。**同时定下交互约定**：**一级 Tab（我的消息 / 我的帖子…）只点击切换**（`TabBarView` 加 `NeverScrollableScrollPhysics`），**左右滑动留给分组内的二级子类型**（帖子 / 评分 / 点评…，用 `PageView` 驱动，见 `message_mypost_tab.dart` / `message_notice_tab.dart`；子类型的 `PageController` 在**确定默认子类型时**才创建，`initialPage` 直接落在它上面，避免先显示第 0 页再跳）。**教训**：凡"运行中可能重建"的 `AnimationController` / `TabController` / `PageController`，一律用 `TickerProviderStateMixin`；控制器长度/页码要跟着**同一份**数据列表走（在 `build` 里派生），别在事件回调里算。
