## 图片

12. **图片查看器用 `photo_view`，不要自己实现** — 手势冲突和缩放动画自己写很难做对，前两版自研实现均已废弃。
13. **图片上传/下载不要用论坛的 `ApiService().dio`** — 图床等第三方域不兼容论坛 Dio 的请求头，上传走独立 Dio；图片下载走 `IgnoreCacheFileService`，过期天数由 `cacheExpire` 配置（`assets/config/cache.json`，见 docs/01「图片缓存规范」）。
14. **`file_picker` 默认压缩图片（GIF→JPG 陷阱）** — `FilePicker.platform.pickFiles(type: FileType.image)` 在 Android 端默认 `allowCompression: true`，Java 端 `FileUtils.compressImage()` 会把图片解码为 Bitmap 后重新压缩为 **JPEG**（硬编码 `Bitmap.CompressFormat.JPEG`），导致：
    - GIF 丢失动画、变为静态 JPG
    - PNG 等格式被强制转为 JPG
    - 分辨率被压缩（默认 `compressionQuality: 30`）
    
    **修复**：所有 `FilePicker` 调用加 `allowCompression: false`。
    
    这是插件自身行为（AOSP 原生相册即可复现），不要误判成系统相册转格式。验证方法：抓 `FilePickerUtils` 日志，出现 `JPEG_时间戳_.jpg` 即命中。

76. **图片域的 WAF 挑战要靠"回放 Set-Cookie"，`http`/`HttpClient` 跟随跳转不带 Cookie** — 现象：App 里所有 `icdn.binmt.cc`（MT 图床）图片都加载不出，浏览器直接打开或**刷新后**却能显示。**根因**：该图片域由阿里云 ESA WAF 保护，首个请求返回 `307 Temporary Redirect` + `X-Tengine-Error: denied by http_custom`，并在 `Set-Cookie` 里下发 `acw_sc__v2` / `acw_tc` 挑战 Cookie；**客户端必须回传该 Cookie 再请求同一地址**才放行。实测（curl，同一 Dart UA）：无 Cookie → 无限 307（跟 50 跳仍拿不到）；带 `acw_sc__v2` → 200 PNG。浏览器/刷新能行，是因为浏览器自带 Cookie 罐；而 `IgnoreCacheFileService` 用的 `http.get` / `dart:io HttpClient` **跟随跳转时不保留 Cookie**（`HttpClient` 自动跟随还会直接抛 `RedirectException: Redirect loop detected`）。**修复**（`core/utils/cache_utils.dart`）：改用手动跟随跳转的 `_getWithWafChallenge`——`getUrl` 后必须 `request.followRedirects = false`（否则自动跟随先抛异常），逐跳读 `response.headers['set-cookie']` 存入**按 host 的内存 Cookie 表**，下一跳及后续请求带上；因 `package:http` 会把多条 `set-cookie` 用 `,` 合并（Cookie 值可含逗号，见 #26），这里用 `dart:io` 的 `HttpHeaders` 取列表更可靠。**注意**：挑战 Cookie 归属是**按 host**（`icdn.binmt.cc` 与论坛 `bbs.binmt.cc` 各一份），不要指望复用论坛 Dio 的 CookieJar；进程内缓存即可，冷启动首个请求多一个往返。**同类排查**：凡"浏览器能开、App 打不开"，先看响应是不是 3xx 挑战而非 403。

79. **克米列表缩略图的 `src` 是懒加载占位图，真实地址在 `comiis_loadimages`** — 现象：导读/板块列表的帖子缩略图"获取失败"，解析出的 `images` 全是 `https://cdn.binmt.cc/template/comiis_app/pic/none.png`。**根因**：克米模板缩略图是自定义懒加载——服务端 HTML 里 `<img src="…/pic/none.png" comiis_loadimages="真实地址" class="comiis_noloadimage comiis_loadimages">`，`src` 只是占位（进入视口后由 JS 换回真实地址），而 `ComiisCardParser` 取的是 `src`（且无 `data-src`）。**修复**（`core/app/thread_parsers/comiis_card_parser.dart`）：按 `comiis_loadimages → data-src → data-original → file → src` 取第一个**非占位**值，并过滤 `none.png` / `nophoto.*` / `loading.*` 占位图（与 `Html2BBCode._placeholders` 同源）。**关键**：懒加载属性与直接 `src` 会**同时存在**（已在视口内的图两者都是真实地址），所以不能"二选一"——必须懒加载优先、`src` 兜底。**排查提醒**：凡是"图片地址解析出来是 `none.png`/`nophoto.gif`"这类占位图，先怀疑模板的懒加载属性，去原始 HTML 里找 `data-src`/`file`/`comiis_loadimages`，别去动渲染层。验证：`guide.list` 探针 + `test/thread_parser_test.dart` 参数化用例。

87. **头像重定向映射会「永久卡住旧 CDN」：站点换头像域名后，持久化的映射让 App 一直下载已失效的旧地址，且失败被静默重抛** — 症状：**能显示别人的头像，唯独自己的（或个别用户的）不显示**，且每次冷启动都重新 `[CACHE] download`（不命中缓存）。**排查路径（可复用）**：① `[CACHE] download:` 只代表"进了真下载分支"（`IgnoreCacheFileService.get` 无条件先打印），**下载失败时它静默重抛、不打错误日志**（非 CDN 域 `originUrlForCdn` 返回 null → 直接 `throwWithStackTrace`）——所以"只有 download、没有报错、图片不显示"即"下载拿到非 200"。② **别猜 URL 生成，直接读磁盘上的映射库**：`%APPDATA%\qcxs\mtbbs_debug\mtbbs.sembast`（sembast 单文件，每行一条 JSON）里 grep `"store":"avatar_redirects"`，就能看到全量「原始 `avatar.php` URL → 最终静态 URL」映射。本次实测：325 条里 **230 条指向新 CDN `cdn.binmt.cc`（活）、仅 1 条指向旧 CDN `cdn-bbs.mt2.cn`（504）——那一条正是用户自己**（`avatar.php?uid=88062&size=middle` → `cdn-bbs.mt2.cn/…/62_avatar_middle.jpg`）。③ 用探针 `debug.http --path=<完整URL>` 逐个验状态：旧地址 **504**、`cdn.binmt.cc/…` **200**，且 `avatar.php` 当前 301 目标已是 `cdn.binmt.cc`。**根因链**：`UserAvatar._schedule` 命中持久化映射就**跳过 HEAD 直接信任**该最终 URL → 下载 504 → 不缓存 → 每次重启重下、永远用旧域名。旧映射本应靠 TTL（=头像缓存周期，默认 7 天）过期，但该条 `updatedAt` 落在**未来**（`now - updatedAt` 为负 → `_isExpired` 恒 false）→ 永不过期；若用户把头像缓存设为「永不过期」(-1) 更是全库都不过期。**修法（两处自愈）**：① `AvatarRedirectStore` 新增 `invalidate(url)`（作废单条 + 持久化删除），`_isExpired` 增加"时间戳在未来一律视为过期"的护栏；② `UserAvatar` 的 `CachedNetworkImage.errorWidget` 首次失败时 `invalidate(原URL)`，并在 post-frame 里 `_scheduledOnce=false; _resolvedUrl=null; _schedule()` 重新 HEAD（每 uid 只自愈一次，避免断网时无限重试）。验证：`test/avatar_redirect_store_test.dart` 新增 `invalidate` 与"未来时间戳视为过期"两例。**通用教训**：凡是"把一次解析结果持久化、之后据此跳过网络请求"的优化，都必须给**失败**留一条自愈通道（换 CDN / 换域名 / 302 目标变更都会让缓存永久指向死地址）；另外 `updatedAt` 这类时间戳要防"落在未来"（设备时钟回拨）。

91. **「生成图片」分享卡：固定浅色 + 超长内容必须分块截图再拼接** — 实现见 `pages/thread/thread_share_page.dart` + `services/image_export.dart`（**方向、扩展步骤与复用清单见 `docs/22`**；做法参考 PiliPlus 的 `SavePanel`，见其 `pages/save_panel/view.dart`）。三个关键点：① **分享卡强制浅色**——把卡片单独包一层 `Theme(ColorScheme.fromSeed(seedColor, brightness: light))`，**不跟随 App 夜间模式**；否则夜间用户截出来是深色图，分享到浅色场景观感突兀（本项目已定策略：固定浅色，不做主题跟随）。② **超长内容必须分块渲染 + CPU 拼接，不能一次 `toImage`**——一次成图在长内容下会触 GPU 单张纹理上限（常见 4096），只能降采样 → **超长帖分享图很糊**（曾据此踩坑）。改法：用底层 `OffsetLayer.toImage(rect, pixelRatio)` 按高度分块（每块 ≤ `_maxTilePx`）逐块渲染，各块 `rawRgba` 拷进一张大缓冲，再用纯 Dart 的 `image` 包 `encodePng` 输出——任意长度都保持 3x；另给总像素设预算（`_maxOutputPx`，32M）防 OOM，仅极长内容才降采样。**取 layer 的两个坑**：`RenderObject.layer` 是 `@protected`（外部访问被 lint 拦），而 `debugLayer` 在 release **恒返回 null**；故自定义了 `RenderRepaintBoundary` 子类 `CaptureBoundary` 暴露 `offsetLayer`（`lib/services/image_export.dart`），分享页与测试都用它替换 `RepaintBoundary`。③ **分平台保存**——Android/iOS 走 `gal`（自带 `hasAccess/requestAccess`，10+ 走 MediaStore 免权限，仅需清单 `WRITE_EXTERNAL_STORAGE maxSdk 29`），桌面走 `FilePicker.saveFile` 另存为；**刻意不做外部分享**（`share_plus` 在桌面端文件分享不可靠，PiliPlus 也只在移动端显示分享按钮，故最小闭环直接剪掉）。**卡片页脚标注 `tid/pid/楼层` 作为站内定位信息**（凭此可在论坛找到该楼）。**图片内容范围 / 生成页勾选项**：默认 = 作者信息 + 正文 + **评分/打赏记录**（`PostItem.rating`：头像 + 用户名 + 各维度分值 + 理由，见 `_RatingSection`）+ 页脚（定位信息 + 右下角**二维码**"扫码直达"，内容为 findpost 链接）。二维码用 `qr` 编码 + 自绘方块（**不要用 `pretty_qr_code`**：它断言「单模块 ≥ 2px」，64px 的二维码会直接抛 `Failed assertion: 'min <= max'` 崩掉）。「是否渲染评分 / 是否截断 / 是否渲染二维码」做成**生成页的临时勾选项（默认全开、不持久化）**，切换即时生效；设置里**只保留**「分享图最大正文高度」（截断数，默认 8000 逻辑 px）。截断开启时正文超过上限即裁切、底部渐隐 + 提示查看原帖 / 该楼层（`_ClampedBody`：不可滚动 `SingleChildScrollView` 天然得到"短则原样、长则裁到上限"，靠 `maxScrollExtent > 0` 判断是否真截断）。另有设置「只生成内容图」（**默认关**）= 只出正文，去掉以上所有附加块（此时生成页勾选项隐藏）。**副作用坑（宽屏分享后帖子页"图片重新加载"）**：分享卡会把同一批帖子图片按**不同的解码宽度**再解码一份（`BbcodeImage.memCacheWidth = 显示宽 × 2`），而 Flutter 的**已解码图片内存缓存默认只有 100MB**——宽屏下帖子图按「图片最大宽度 600」解码（1200px，单张大），两份叠加超预算 → LRU 淘汰掉**更早访问的、帖子页自己的**图；返回帖子页时重新解码（表现为"页面被重载 / 布局变了"）。窄屏图小、两份装得下，所以**只有宽屏复现**。注意：`Navigator.push` 本身**不会**重建/释放下层页面（用 widget test 验证过 State 存活），别往路由方向排查。修法（两条）：① **让解码尺寸与布局解耦**——`BbcodeImage` 的 `memCacheWidth` 由"显示宽 × 2"改为 `min(屏幕宽, max(图片最大宽度, 显式宽)) × 2`（只与屏幕/设置有关，与布局无关），同一张图在宽/窄布局、分享卡、编辑器预览下命中**同一条目**，不再各解一份；② 抬高预算 `main()` 里 `PaintingBinding.instance.imageCache.maximumSizeBytes = 200 << 20` 兜底。另把 `BbcodeImage`/`UserAvatar` 的 `fadeInDuration/fadeOutDuration` 设为 0：命中缓存时直接显示、不再淡入，消除"返回页面图片重新加载"的观感。**Esc 返回要自带**：本页用 `Navigator.push` 推到 root，是 ShellRoute 的**兄弟路由**，不在 `GlobalShortcutsWrapper`（挂在 ShellRoute 外层、提供全局 Esc→返回）的覆盖范围内——故 `ThreadSharePage` 自己用 `CallbackShortcuts` 绑了一份（键值跟随设置里的 `goBack`）。凡"push 到 root 的独立全屏页"都要注意这点。**卡片与骨架已拆分复用**：预览骨架（浅色预览 / 截图 / 勾选项 / 保存 / Esc）抽到 `pages/share/share_image_page.dart`（`ShareImagePage.open` + `ShareToggle`），二维码抽到 `widgets/share/share_qr_code.dart`；帖子卡在 `pages/thread/thread_share_page.dart`。**个人主页图 = 整页内容**（需求："与页面完全一致、无需任何配置"）：**不另建卡片**，改为页面内预览模式（`user_profile_page.dart` 的 `_sharing` 开关 + `pages/user/user_share_page.dart` 的 `UserSharePreview`），直接复用页面自己的正文区块（`_contentSections()`，正文列表与图片共用同一份 → 内容 / 主题 / 布局天然一致），因此**不强制浅色**（跟随页面主题）、**无勾选项**；页面区块之外只在底部追加一条「站点（`MTBBS · host`）/ 用户（昵称 · uid）/ 二维码（扫码直达，`ShareQrCode`）」水印。关键点：这些区块内部会调用 `context.select<AuthProvider>`，**只能在 build 中调用**，故必须由页面在其 `build` 里构建好再传入预览（否则需为 `select` 准备回退值）。**已知限制**：正文图片是异步的（`CachedNetworkImage`），未加载完就点保存会截到占位图——重进一次或等图片显示后再保存；`[code]` 块内部可横向滚动，截图只保留可见宽度。**验证**：`test/image_export_test.dart`（PNG 魔数 + **分块拼接用例：200×2400 边界 → 600×7200 长图**，证明输出高度可超单块上限 4096）。
