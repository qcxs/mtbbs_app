## 通用

20. **CSS 属性提取必须锚定声明起点** — 用正则提取内联样式时，`'color\\s*:\\s*([^;]+)'` 这类**未锚定**的写法会把 `background-color:green` 误判为 `color:green`（`color` 是 `background-color` 的后缀），导致 `<font style="background-color:green">` 被转成 `[backcolor=green][color=green]...[/color][/backcolor]` 多套一层。修复：`(?:^|;)\s*${属性名}\s*:\s*([^;]+)`，锚定到声明起点。

21. **MCP 工具优先** — 新增 API 时先用 Chrome MCP 确认请求/响应格式，再写 Dart 代码。
22. **日志强制 AppLogger** — 严禁 `print`/`debugPrint`。注：lint 未做强制阻断——`avoid_print` 在 `analysis_options.yaml` 被 ignore（放行 `tool/` 探针与测试文件的 print），生产代码靠约定执行。
23. **跨 Widget 状态传递用统一实例，不要层层回调** — 同组件树内用 Controller 实例（如 `BBCodeToolbarController`），全局配置用 Provider，都比多层回调易维护。
24. **编辑器页面必须用 PC UA** — 编辑器的 DOM 解析（`PageFetcher.parsePage`）依赖 Discuz PC 版的 HTML 结构（`textarea#e_textarea`、`input#subject`、`a[id^=imageattach]` 等）。用移动 UA 拿到的页面表单字段为空、图片/附件列表无法识别。现在 `ApiService` 默认就是 `Site.uaPc`，编辑器 `fetchPage` 再显式覆写一次——两处都不要改成移动 UA。
25. **UA 才是决定 Discuz 模板的开关，`mobile=2` 只是辅助** — Discuz 按 `User-Agent` 决定返回移动版还是 PC 版 HTML，`mobile=2` 只影响页面内少量呈现。不要靠 `mobile=2` 去"切版本"以适配解析（解析逻辑依赖的是 UA 对应的 HTML 结构）；只有登录页这类需要移动版表单的页面才保留该参数（见 `web_login_page.dart`）。
26. **Cookie 解析需要异常保护** — Discuz 的部分 Cookie 值包含逗号（如 `discuz_lastvisit=ts1,ts2,ts3`），Dart `dart:io` 的 `Cookie(name, value)` 构造函数严格遵循 RFC 6265，禁止 value 中出现逗号，抛出 `FormatException`。修复：`_parseCookieString` 中 `try/catch` 跳过非法 Cookie。
27. **一律用 `package:mtbbs/...` 绝对导入，不用 `../` 相对导入** — 移动文件时不需要改 import。目录重组（`widgets/`、`core/` 分子目录）时已统一转过一次（历史聚合 barrel 已删除，仅保留 `mcp/mcp.dart`、`widgets/image_preview/image_preview.dart`）。
28. **`file_picker` 选取文件时无条件复制缓存副本（Android/iOS）** — 插件 Java 端 `FileUtils.openFileStream()` 在**每次选取**时都把文件复制到 `{getCacheDir()}/file_picker/{时间戳}/{文件名}`，与 `withReadStream`/`withData`/`allowCompression` 都无关——`allowCompression: false` 只绕过了 JPEG 压缩（见 #14），不阻止落盘。该缓存**无自动清理**，插件要求 App 主动调 `FilePicker.platform.clearTemporaryFiles()`（Android 端即递归删 `file_picker/` 目录）；桌面端直接返回原路径不复制，故仅移动端有此问题（Windows 上缓存管理页该项恒为 0）。**修复**：缓存管理页新增「文件选择器缓存」项（复用 `getCacheInfo('file_picker')` / `clearCacheByKey('file_picker')`，即 `{tempDir}/file_picker`）；图片、附件、图床三处上传成功后调 `deleteFilePickerTempIfAny(path)` 自删（仅删 `{tempDir}/file_picker/` 下的副本，按路径前缀严格校验，绝不触碰用户原图；剪贴板图片走 `mtbbs_clip/` 不受影响）。

61. **Windows 标题栏一律自绘，不要指望 `setBrightness` 去调原生栏** — 踩坑链条：`window_manager`（0.5.2）Windows 端的 `SetBrightness`（`windows/window_manager.cpp`）实现是 `enable_dark_mode = (系统 AppsUseLightTheme == 0) && (应用主题 == dark)`——**只有「系统深色 + 应用深色」这一个组合**才把标题栏切深色，其余情况一律 `FALSE` 回落到系统默认；且 `DwmSetWindowAttribute(DWMWA_USE_IMMERSIVE_DARK_MODE)` 需要窗口重绘才生效，而我们是在 `show()` 之前下发。于是原生标题栏的底色/字色由「系统主题 + 应用主题 + 注册表值」三者共同决定，App 拿不到控制权——实测出现白底白字、按钮"看不见"，且**反复调 `setBrightness` 都无法稳定得到正确配色**（这也是它被反复"修"却修不好的原因）。**做法**：Windows 下固定 `TitleBarStyle.hidden` + `windowButtonVisibility: false`，由 `WindowChrome` / `WindowTitleBar` 自绘标题、MCP 徽章与最小化/最大化/关闭按钮，颜色一律取自 `Theme.of(context).colorScheme`，深浅模式必然可读；同时移除"显示窗口标题栏"设置项，杜绝切回不可控的原生栏。`syncWindowBackground(brightness)` 只负责窗口底色（避免首帧前露反色）。最大化时的客户区溢出由 window_manager 的 `WM_NCCALCSIZE` 分支自行补偿，无需额外处理。

62. **`MaterialApp.builder` 里不能放依赖 Overlay / Material 的组件** — 自绘窗口标题栏一度放在 `MaterialApp.builder`，一启动就报 `No Overlay widget found`（Tooltip 需要 Overlay）并把整屏变红，还连带 `RenderFlex overflowed by 298955 pixels` 这种夸张的连锁异常。原因：`builder` 包在 **Navigator 之外**，既没有 Overlay（Tooltip/菜单/对话框都要）也没有 Material（InkWell 水波纹要）。**规则**：需要这些祖先的全局外壳组件，放到 **壳路由（`ShellRoute` 的 builder）里**——那已在 Navigator/Overlay 之内；确实要放 `builder` 就自己套 `Overlay`/`Material`。**排查提醒**：真机 `flutter run` 的控制台日志是唯一能发现这类"渲染才炸"问题的手段（见 docs/17）。

63. **MCP 的 DNS rebinding 白名单不能写死 Origin，否则 Chromium 系客户端被 403 且报错毫无线索** — 现象：Trae 连本机 MCP 只报一句 `list tools failed`，App 侧日志什么都没有。**排查路径**（值得复用）：① `curl` 不带 Origin 请求 `tools/list` → 得到 `400 No valid session ID`，说明**鉴权已过、服务端活着**（否则会是 403）；② 补齐 `initialize` → `notifications/initialized` → `tools/list`（带 `mcp-session-id`）后**完整返回全部工具**，反证服务端与工具表都正常；③ 逐个试 `Origin` 头才发现真凶——带 `http://127.0.0.1:8765` 的请求 `403 Forbidden: blocked by DNS rebinding protection`。**根因**：`mcp_dart` 的 `isRequestAllowedByDnsRebindingProtection`（`lib/src/server/dns_rebinding_protection.dart`）——**显式传 `allowedOrigins` 时要求 Origin 字符串精确相等（含端口）**，而我们写的是不带端口的 `http://127.0.0.1`，Trae 发的是 `http://127.0.0.1:8765` → 不匹配。**修复**：**不传** `allowedOrigins`；SDK 会退化为「Origin 的 host 必须属于 `allowedHosts`」，任意端口的回环 Origin 均放行，安全性等价（非回环 Origin 照样被拒，另有 Host 校验与 Bearer 令牌两层）。**附带两点**：SDK 对 `Origin: null` 是硬编码拒绝（与白名单无关）；`McpProtocol.stable` 下 `2026-07-28` 走无状态分支，要求 HTTP 头 `Mcp-Method` 且 `params._meta` 带 `protocolVersion`/`clientCapabilities`，缺任一项都会 400。

64. **Flutter 3.27 起自带的 deep link 处理默认开启，自研 intent 通道必须显式关掉它** — 现象：从系统「打开受支持的链接」进 App 报 `GoException: no routes for location: <完整论坛 URL>`，而且**冷启动与热启动表现不一致**（一会儿行、一会儿不行）。根因：Flutter 3.27 把 `flutter_deeplinking_enabled` 的默认值由 `false` 改为 `true`（官方 breaking change），自带的 deep link handler 会把 intent 里的**完整 URL** 直接交给 GoRouter——**冷启动**当作 `initialRoute`、**热启动**走 `RouteInformation` **运行时推送**。我们有自己的 `AppLink` 通道（即官方所说的"第三方处理方式"），所以必须显式关闭它。**优雅解法（一行）**：在 `AndroidManifest.xml` 的 `<activity>` 内加
```xml
<meta-data android:name="flutter_deeplinking_enabled" android:value="false" />
```
**反面教材**（这次先走了弯路，勿重蹈）：用 `overridePlatformDefaultLocation: true`、在 `onCreate` 里把 `intent.action` 改成 `ACTION_MAIN` 并清 `data`、再给 GoRouter 加 `redirect` 兜底——这三样都**只能挡住冷启动**那条（`initialRoute`），热启动是运行时推送，绕不过去，于是"加完看着好了，一测又崩"。**排查提醒**：遇到"同一个链接有时行有时不行"，先怀疑**冷启动/热启动是两条通路**，而不是去猜 URL 解析。**顺带**：链接落地逻辑已收敛为唯一决策点 `UrlRouter.resolveTarget(url)`（App 内路由优先 → 兜底 `/browser?...&intercept=false`），首页、帖子正文、系统入站三处共用。

65. **前台服务不会随"退出应用"自动结束，通知必须显式收尾** — 现象：返回键退出（双击退出 → `SystemNavigator.pop()`）后 MCP 常驻通知仍在，进程也一直被留在前台服务级别。根因两条：① Android 上 `SystemNavigator.pop()` 只是 `activity.finish()`（Flutter 文档原话是 "removes this activity from the stack"），**不杀进程**；`FlutterActivity` 销毁时确实会 `destroy()` 掉 FlutterEngine（Dart 侧 MCP HTTP 服务随之停止、端口释放），但 `McpForegroundService` 是独立组件、继续存活 → 通知成了「MCP 服务已开启」的假状态（服务早就没了）。② `<service>` 的 `android:stopWithTask` **默认 false**，所以从最近任务划掉 App 也**不会**停止前台服务（`onDestroy` 都不被调用），"划掉就自动消失"的想法不成立。**修复**：返回键路径在 `MainActivity.onDestroy()` 里判 `isFinishing` 调 `McpStatusNotification.stop()`；划掉任务路径给 service 加 `android:stopWithTask="true"`。**教训**：凡是"前台服务 = UI 状态的呈现"，其生命周期必须与 Activity 显式绑定收尾，不能指望"进程结束服务就结束"；也不要反过来在 `onStop` 里停——应用切后台、Activity 未销毁时 MCP 仍要能服务 AI 客户端。停掉服务后进程回到 cached、由系统按内存压力回收，这才是 Android 的正常退出语义。

66. **楼层号必须按 postnum 标签解析，不能按列表下标推算** — 现象：帖子页评论第 1 页显示 1-15，翻到第 2 页又变回 1-15（每页重新计数）。根因在 `parsePostFromTable` 的楼层提取：`RegExp(r'#(\d+)')` **方向写反了**——克米模板的标签是数字在前（`<a id="postnumXX"><em>16</em><sup>#</sup></a>` → `16#`），标准 Discuz 才是 `#16`；同时前 10 楼是中文名（楼主/沙发/椅子/板凳/地毯/凉席/报纸/地板/地下室/下水道），本就没有数字。两条路径都取不到值，`floor` 便一直保留调用方传入的下标兜底（`page>1` 时 `i+1`），于是每页都从 1 开始。**判定依据**：楼层编号是全帖连续的——楼主 = 1 楼，下水道 = 10 楼，紧随其后的帖子正是 `11#`（站点还给 `km1..km4` 类名，可交叉验证 楼主/沙发/椅子/板凳 = 1/2/3/4）。**修复**：`parseFloorFromLabel` 同时支持 `(\d+)#` 与 `#(\d+)`，并加 `_namedFloors` 中文名映射；展示层 `PostItem.floorText` 允许中文楼层名原样显示，数字仍渲染为 `#N`。**教训**：任何"每页从 1 开始"的楼层推算都会在翻页时重号，下标只能当解析失败后的兜底，不能当主逻辑。

67. **跨平台插件的方法在部分平台是直接 `throw UnimplementedError`，用前先确认该平台是否实现** — 现象：App 侧（Dio）`misc.php?mod=userstatus` 正常返回已登录（uid/用户名都对），但**内置浏览器显示未登录**——两边"看起来"是同一套 Cookie 却表现不一致。根因：`BrowserPage._syncCookies()` 的清理步骤用了 `CookieManager.getAllCookies()`，而 Windows 端**没有实现**它——`flutter_inappwebview` 的 `PlatformCookieManager.getAllCookies()`（`flutter_inappwebview_platform_interface/lib/src/platform_cookie_manager.dart:288`）直接 `throw UnimplementedError('getAllCookies is not implemented on the current platform')`。Windows 实现只覆盖 `setCookie` / `getCookies` / `getCookie` / `deleteCookie` / `deleteCookies` / `deleteAllCookies`（Android 有 `getAllCookies`，所以这是 **Windows 独有的坑**，本机开发时才发现）。**放大器**：`_syncCookies` 当时是一个大 `try` 包住「清理 + 注入」两步、末尾 `catch (_) {}` 静默吞掉——清理一抛异常，**后面的注入被整体跳过**，WebView 里没有账号 Cookie → 表现为"未登录"。症状（登录态没同步）与原因（清理抛异常）完全对不上，排查时极易往错误方向猜。**修复**：① 改用 `getCookies(url:)`——Windows / Android 都已实现，且它天然只返回该 URL 适用的 Cookie，等于已经按站点隔离，连按 domain 过滤都省了（顺带修掉"Android 的 `domain` 缺 `GET_COOKIE_INFO` 时为 null → 过滤条件把全部 Cookie 跳过"的隐患）；② 把「清理」和「注入」拆成两个独立 `try/catch` 并各自 `AppLogger.w` 留痕，两步互不连累。**教训**：① 调插件 API 前先确认目标平台有没有实现——`PlatformXxx` 基类的默认实现就是抛 `UnimplementedError`，"能在文档/IDE 里搜到方法"**不等于**"各平台都实现了"；② 同类 API 优先选**带 url 参数**的版本，它语义上限定作用域，两端实现也更全；③ **串行步骤绝不要用一个大 `try` 包住**，前一步失败会静默吞掉后面所有步骤，而 `catch (_)` 让平台异常彻底隐形（与全篇反复强调的"失败要留痕、不要静默吞掉"是同一类病）；④ 平台 API 无法单测，更要靠日志留痕——这次若当初就打了 WARN，一眼就能看到 `UnimplementedError`。

68. **不要把"自己的输出"序列化后再读回来——HTML 里的值不是数据** — 症状：编辑器预览里点图片右上角"看大图"，画廊纯黑且没有任何报错，同一张图的内联预览却完全正常。**根因**：编辑器里已绑定的图片是 Discuz 带参附件地址（`forum.php?mod=image&aid=…&key=…`，结构见 `page_fetcher.dart` 注释）。转换层 `htmlEscape` 把 `&` 写成 `&amp;` 才存进 `<img src="…">`，渲染器解析 HTML 时又解码回 `&` —— 于是"渲染层拿到的值"与"从 HTML 字符串正则回读拿到的值"是两个不同的串。画廊列表当时正是**在生成的 HTML 上正则回读 `src`**，取到未解码的 `&amp;` → 请求 404 → `PhotoViewGallery` 又没设 `errorBuilder`，只剩黑底，零线索。**根治**：需要交给渲染层的结构化数据（URL 列表 / 代码原文 / 索引）必须在**产出 HTML 的同一处**记录成公开字段（发射点记录），不在 HTML 上做二次读取。实现：`_emitContentImage(url, tag)` 把"可直接使用的 URL"与待落地的 `<img>` 一起存进 `_imageSlots` 并返回 `\x00IMG*` 占位符，最后 `_resolveContentImages` 按占位符在 HTML 中出现的位置展开为 `data-img-index`（并填充 `imageUrls`）——与 `[code]`/`codeBlocks` 是同一套占位符范式（见 #31）。顺带解决两件事：① 顺序天然是**文档顺序**（`[appdata]` 图片在步骤 0 就渲染、早于 `[img]`，按发射顺序收集会颠倒）；② 表情 `<img>` 不走占位符，因此不再需要用字符串判别 `data-type="emoji"`。**规则已固化**：docs/02「数据层 ↔ 渲染层职责边界」。**附带教训**：任何全屏/黑底容器都要设 `errorBuilder`（或等价的失败提示），否则"加载失败"与"还在加载"在用户眼里都是纯黑。

71. **`flutter_inappwebview` 的「删除 Cookie」在 domain 为 null 时只删 host-only 那条，且静默** — 症状：内置登录页明明"清过 Cookie"，却仍带着上一个账号的登录态，换不了账号。**根因**（读 `flutter_inappwebview_android` 的 `MyCookieManager.java`）：① `getCookies` **只在 WebView 支持 `WebViewFeature.GET_COOKIE_INFO` 时才回填 `domain`**，否则 `cookieMap.put("domain", null)`；② 原生 `deleteCookie`/`deleteCookies` 都是 `if (domain != null) cookieValue += "; Domain=" + domain;` —— domain 为 null 就**不写 `Domain=` 属性**，只会命中 host-only 形态。两者叠加：Discuz 那种 `Domain=.bbs.binmt.cc` 的**域 Cookie 永远删不掉**，而且接口照样返回成功（`successful=true` 只代表 setCookie 调用成功，不代表删掉了东西）。**修复**：`clearCookiesForHost` 对每条 Cookie 按候选 domain 各删一次（`null` → host-only；`.{host}` → 最常见的域 Cookie；平台回填值若有）。删除不存在的 Cookie 是无副作用的空操作，多试几次的代价可接受。**另一处独立缺陷**：`WebLoginPage.initState` 里 `clearCookiesForHost(...)` 是 fire-and-forget，而 WebView 在同一帧就带着旧 Cookie 发起加载——现在加 `_cookiesCleared` 闸门，清完才创建 WebView。**教训**：跨平台插件的"删除/清理"类接口，**返回值往往只表示"调用成功"而不是"目标被处理"**（与 #67 同一类病）；凡是要"确保为空"的场景，要么逐字段核对，要么按所有可能的写法各做一次，别信一次调用的返回值。

72. **UA 会被站点的一条 Cookie 完全压掉：Discuz 的「浏览方式」优先级高于 UA 嗅探** — 症状：App 里明明选了「移动版」，某天开始**所有**请求都按 PC 模板返回；**重新登录无效**，但**换一个账号就正常**。**根因**：站点在"该页面无手机版"的提示里给了个「继续访问电脑版」链接（`…&mobile=no`），点它会下发 `Set-Cookie: {前缀}_mobile=no; Max-Age=3600`（MT 论坛前缀 `cQWy_2132_`）。优先级是 **`?mobile=` 参数／`*_mobile` Cookie > UA**，所以此后该 CookieJar 的所有请求都被强制 PC 模板，UA 不再参与决策。实测同一手机 UA、同一 URL：罐内无它 → 173.5 KB 移动卡片；有它 → 89.0 KB PC 表格。**三个"怪现象"的解释**：① 重登没用来自身份 Cookie 与它无关、且 `Max-Age` 被反复续期；② 换账号正常是因为 CookieJar **按账号隔离**（`cookies/{host}/{账号}/`）；③ 站点配置（`Site.userAgent`）查下来仍是移动 UA —— **别被带偏去怀疑设置项**。**修复**：`ApiService._dropBrowseModeCookie()` 按后缀 `_mobile` 把该条从**请求头**里摘掉，必须排在 `CookieManager` **之后** —— 后者才是把罐里 Cookie 合成 `cookie` 头的那一步（`cookie_jar` 4.0.9 无按名删除接口，`delete` 是按 URI 整体删，所以不动罐、只改请求）。**教训**：排查"UA 失效"这类问题时，**UA 只是决策链的一环**，站点侧参数/Cookie 的优先级可能更高；先验证"服务端到底依据什么决策"（对比同一 UA 下罐里有无该 Cookie 的返回），再动 App 的设置。

73. **人机验证 cookie 反复失效：先怀疑"没落盘"，别只看请求链路** — 症状：验证通过后当场正常，**退出重进又弹**。两层原因：① **归属**——验证 / 防火墙 cookie 是**客户端级**的（与账号无关），却只写进"当时活跃的那个罐"，而罐按 `{host}/{账号}` 隔离，切账号 / 切站点 / 重启落到另一只罐即丢（实测游客罐有 `acw_sc__v2`、账号罐有 `acw_tc`，各持一半）。修法：验证通过后把新拿到的 cookie **补写到本站点每个罐**（见 `ApiService.mirrorToAllJarsForHost`）。曾试过"站点共享罐 + 合并视图"，放弃是因为它得额外回答准入 / 优先级 / 何时刷新三个问题；补写进每个罐则三者都不存在。**同类归属 bug**：游客态恢复必须回到游客罐（`cookies/{host}/`），别拿 `'游客'` 当账号名去建空罐。② **落盘**——`cookie_jar` 4.0.9 的 `PersistCookieJar._filterPathEntries` 落盘时直接调 `cookie.isExpired()`、**绕过 `ignoreExpires`**（内存侧是尊重的），而各端 `Cookie.expiresDate` 的单位/含义都不可信：Windows 给的是 CDP 的 `expires`（**秒**），Android 支持 `GET_COOKIE_INFO` 时算 `currentTimeMillis() + maxAge` 而 `maxAge` 是**秒**（得到"现在 + N 毫秒"的瞬时过期值）→ 该 cookie 在**后续某次保存**时被判过期、从磁盘上消失（当次会话完全正常，重启即失忆；Android 因这个算法尤其明显）。修法：`toJarCookies` **一律不带 expires**（App 的罐本就不按过期丢 cookie）。③ **登录态被污染（最终真凶）**——登录时把 WebView 的**全部** cookie 存成了 `Account.cookieString`，防护 cookie（`acw_tc`/`acw_sc__v2`）因此被当成账号身份存了下来（实测某账号里躺着一条 **9.7 小时前**的 `acw_tc`）。于是每次启动 / 切账号 / **导入导出**都用这条旧值覆盖罐里刚刷新出来的新值 → 服务端只肯回挑战页 → 永远刷不新，形成"每次冷启动都要验证"的死锁。这也解释了"新装正常、老装与导入后必坏"，以及"导出能把故障搬到别的设备"。修法：**cookie 分「核心 / 临时」两类，登录态只存核心**——核心是站点自己的会话身份，判据取 Discuz 判定登录的 `{cookiepre}auth`（`cQWy_2132_auth` 去掉 `auth` 即前缀），推不出时退化为"出现 ≥2 次的下划线前缀"统计；临时 cookie（防护、站点配置）只留在 CookieJar 里由响应按需刷新，不进登录态、不注入 WebView。三处统一走 `cookie_sync.dart` 的 `inferCookiePrefix` / `isCoreCookie` / `coreCookiesOf`：**捕获（登录）/ 恢复（解析 cookieString）/ 注入 WebView**。验证：设备上连续 3 次冷启动，0 次拦截。**排查法**：凡"重启后才失效"，直接看磁盘上的持久化文件——桶存在但**条目为空**即为静默过滤；有 adb 时更省事：`adb exec-out run-as <pkg> cat files/…` 直接读罐文件 / `mtbbs.sembast` / `app_webview/Default/Cookies`，比加日志更快定位（本次就是靠它一步定死的）；用 `flutter run` 的 `R` 热重启复现，用 `tool/api_probe_test.dart` 注入磁盘 cookie 打同一 URL 做隔离实验（见 docs/10）。**教训**：日志"写入 N 条"只证明调用没抛异常、**不等于落盘**；跨平台插件的**时间戳单位必须实测**，别默认毫秒（与 #71「插件返回值只代表调用成功」同类）。挑战本身的机制（ESA / `acw_sc__v2` / 两级恢复）见 `docs/20-人机验证与站点防护.md`。

80. **阿里云 ESA 的 `acw_sc__v2` 挑战可以本地自解；"反复验证"是客户端不能自解造成的，不是站点节奏** — 站点未过挑战时返回 200 + 4KB 挑战页（`server: ESA`、`x-tengine-error: denied by http_custom`），页面 JS 用 `arg1` 算出 `acw_sc__v2` 写 Cookie 后 `reload()`；浏览器毫秒级静默完成，**实测纯浏览器 11 次导航 / 4 分钟、含快慢节奏与并发，0 次重验证** —— 所以"短时间内反复验证"不是站点风控，而是 App 没有 JS 引擎：每次 token 需刷新时只能弹 WebView，用户就"看见"了浏览器里看不见的那次刷新。修法：**本地自解 + 原样重放**（App 用内嵌 JS 引擎执行真实脚本，探针用纯 Dart 复现算法），解不出来才落回人工验证。两个硬坑：① `acw_sc__v2` 只与服务端**本轮**为同一 `acw_tc` 下发的 `arg1` 配对，**把浏览器里复制的 cookie 灌给 Dio 会失效**（别再沿用"复制 cookie 绕过"）；② 挑战脚本的函数 `b()` 会**故意递归到栈溢出**做反调试、靠 `catch` 吞异常，JS 引擎栈上限若用默认 1 MiB 会**先炸原生线程栈**（进程 `0xC00000FD`，Dart 侧无任何异常），须调到 256 KiB。机制全貌、两级恢复设计与将来滑块类验证的预案见 `docs/20-人机验证与站点防护.md`。

92. **弹层（bottom sheet / dialog）的内容必须"可滚动或有界"，否则任何长度可变的内容都必然溢出** — 现象：私信页发送失败后点叹号弹出的「重新发送 / 删除」面板（`pm_chat_page.dart`），**错误文案一长就 `RenderFlex overflowed`（黄黑条纹）**。**根因（两类容器都不自动滚动）**：① `showModalBottomSheet` 给内容的高度上限是**屏高的 9/16**（未开 `isScrollControlled` 时）；② **`AlertDialog.content` 完全不会**自动滚动。把长度可变的内容直接塞进一个**非滚动**的 `Column(mainAxisSize: MainAxisSize.min)`（长文本、或 `.map()` 直接铺出的不定长列表）就一定会超过上限。**判别**：这块内容长度会不会变？会变（服务端错误串、BBCode 原文、URL、帖子标题、账号/选项列表…）→ 必须能滚动。**修法**：外层包 `SingleChildScrollView`（内容短自动贴合、超出即滚动，**不需要手算高度**——`SingleChildScrollView` 按 `constraints.constrain(childSize)` 取尺寸）；列表类用 `Expanded + ListView` 且弹层 `constraints` 给 `maxHeight`（见 #53）；`AlertDialog` 只需把 `content` 包一层。**注意 `SelectableText` 不滚动时只是被裁剪**（用户看不到后面的内容且**没有**黄黑条纹），比 overflow 更隐蔽。**本次全局排查（一次同类缺陷，均已修）**：`pm_chat_page` 失败面板、`thread_view_actions._showBbcodeDialog`（BBCode 原文）、`formula_dialog`（积分公式）、`image_utils.showImageInfoDialog`（URL）、`emoji_management._showEmojiDetail`（图片 URL）、`mcp_token_dialogs._TokenDetailSheet`（备注/令牌）、`browser_page_actions._showAccountSwitch`（账号数量不定）、`bbcode_dialog`（9 项样式标签）、`favorite_page._confirmDelete`（帖子标题）、`mcp_quick_dialog`（错误串），以及通用组件 `pages/settings/widgets/dialogs.dart` 的 `showNumberDialog` / `showSelectDialog` / `showMultiSelectDialog`（组件本身无界，防止后续调用点踩坑）。**教训**：这是"**基础容器约定**"级别的坑——凡写弹层，先问一句"内容会不会比弹层高"，把"可滚动"当默认动作，而不是等用户报溢出。规范已固化进 `docs/02`「通用 UI 规范」。

98. **Windows 上 `File.copy` 会保留源文件的 LastWriteTime，按 mtime 清理缓存会误删刚复制的新副本** — 症状：从资源管理器复制一张旧图片到编辑器粘贴，上传报 `PathAccessException: Cannot open file ... errno = 32（另一个程序正在使用此文件）`；截图粘贴却正常。**根因**：`ClipboardPasteService` 把剪贴板文件复制进 `{temp}/mtbbs_clip/` 后立刻 `unawaited(_cleanCache())`，而 Windows 的 `CopyFile` **保留源文件 mtime**；源图修改时间超过缓存周期（1h）时，新副本被当成过期缓存删除，恰好与上传打开文件撞车 → 共享冲突。**修法**：复制后显式 `dest.setLastModified(DateTime.now())`（刷新失败也不丢文件）。**教训**：凡"复制文件进缓存 + 按 mtime 清理"的组合，都必须重置副本时间戳；PowerShell 写出的原始图片因 mtime 是当前时间，才没暴露该问题。

104. **Windows 最大化时 `Tooltip` 会撞上框架断言 `size == theater.size`——窗口几何变化期间要禁掉 Tooltip** — 现象：最大化窗口后，浮到首页某个 `IconButton` 上就抛 `'package:flutter/src/widgets/overlay.dart': Failed assertion: line 2850 pos 12: 'size == theater.size'`，`error-causing widget` 指向那个带 `tooltip` 的 `IconButton`，约束是**变化前**的旧窗口尺寸（如 954×680）。**根因**：`Tooltip` 用 `OverlayPortal` 渲染浮层，浮层子树由 `_RenderDeferredLayoutBox` 延迟布局；窗口尺寸在同一帧内变化时，theater 已按新尺寸布局，而延迟子树仍拿着旧 tight 约束重排，框架在 `_computeNewLayoutInfo` 里断言两者一致。**修法**（`window_title_bar.dart`）：窗口监听器在 `onWindowResized/onWindowMaximize/onWindowUnmaximize`（以及点击自绘最大化按钮的**同步段**）里 ① `Tooltip.dismissAllToolTips()` 收掉正在显示的浮层；② 把 `TooltipVisibility(visible: false)` 包在整棵子树外并防抖 300ms 后恢复——`Tooltip` 在不可见时**根本不创建** `RawTooltip`，也就没有 overlay 子节点。**注意**：这是框架侧的 debug 断言，release 下不崩但可能错位，别当作"只在 debug 出现就无所谓"；抑制窗口只需覆盖"最后一次尺寸变化后的短暂时间"，不要做成常驻开关（会连带失去 tooltip 与无障碍语义）。

102. **网宿 WZWS 是「跳转式」挑战：通行证是 `?wzwschallenge=` 跳转，不是 cookie** — 52pojie 前置网宿 WAF，未过挑战时返回 **200 + 约 36 KB 混淆脚本**（响应头 `WZWS-RAY`，无 `server: ESA`），**没有 `arg1`、没有 `Set-Cookie`**。**最容易误判的一点**：脚本既不写 `document.cookie`、也不发 XHR —— 在 Node 最小 DOM 桩里跑完"看起来什么都没发生"（只看到 `setInterval(…, 4000)`），于是很容易得出"这种挑战无 cookie 可拿、只能弹 WebView"的结论。`setInterval` 里挂的是 `while(true)` 递归反调试（**永不执行回调即可规避**），真正的逻辑被控制流平坦化 + 字符串数组藏住了，**`npx webcrack` 反混淆才能看到**：它只做一次 `window.location = "/WZWSREL<base64>?wzwschallenge=<标签>&wzwsinfos=<base64 JSON>"`。该地址 **302 回原路径**，之后普通请求直接给真实页面（服务端按 IP+UA 指纹放行，**全程不需要任何 cookie**）。**修法**：桩里用 `Object.defineProperty` 捕获 `window.location` / `document.location` 的**赋值**（读返回伪 location、写记下目标地址），脚本跑完把地址交给 Dart，用同一个 Dio **同站 GET** 该地址（校验 `target.host == base.host`，带 `kInterstitialHandledFlag` 防递归），成功即重放原请求；任何一步失败返回 false → 自动回退 L2 WebView。**排查提醒**：① "沙箱里什么都没发生" **不等于** 脚本没动作，先确认桩有没有**监听它可能改写的对象**（`location`/`history`/`document.cookie`）；② 该挑战只在**非浏览器 HTTP 指纹**（PowerShell / 原生 HttpClient 等）下出现，真实 Chrome 与 App 常规请求都没见过，做成 L1 属**兜底**而非常态路径。机制见 `docs/20` 第一节表，代码在 `lib/core/app/js_challenge_solver.dart`。

105. **Dio 拦截器不能复用"创建时捕获"的 CookieJar / baseUrl：切账号、切站点后它们是旧的** — 症状：MT 论坛人机验证**过不去**（本地自解没生效、页面一直报错），而上一版正常；错误页只有「重试」，**不再回退 WebView**。根因（无状态化引入的回归）：`_createDio(baseUrl, jar)` 把 `jar` / `baseUrl` 捕获进响应拦截器，但全局 Dio 的这两样在运行时会被换掉——`switchToAccount` / `switchToGuest` 走 `_replaceCookieManager` 换的是**外层字段** `_activeJar`，`switchSite` 改的是 `dio.options.baseUrl`；闭包里的仍是 init 时的游客罐与旧站点。于是 L1 把 `acw_sc__v2` 写进了**已被替换的旧罐**（默认请求带的是新罐，看不到它），或按**旧站点域** `.\{oldHost\}` 写（新站点不发送）→ 重放仍被拦；更糟的是 L1 返回了 `true`（"写 cookie 成功"），`_recoverFromInterstitial` 不会再走 L2，所以既没有 WebView、也没有可解释的错误。**修法**：拦截器按 `isGlobal`（构造时显式传入，别用 `identical(d, dio)`——`dio` 是 `late final`，作用域 Dio 若早于 init 发请求会炸）区分：全局 Dio 在**每次响应时**取 `activeCookieJar` 与 `d.options.baseUrl`，作用域 Dio 用创建值。**连带修的三处**：① L2（`VerificationGate`）改为接收 `InterstitialContext{client, jar, baseUrl}`，探针与 cookie 回流都落到**这次请求自己的罐**，跨站点会话也能弹验证（此前 `allowHuman: isGlobal` 直接禁掉了）；② `SessionRegistry.refreshHost` 跳过"当前站点"——它用全局 Dio，再建一份作用域会与全局罐指向**同一目录**，两个 `PersistCookieJar` 实例各持内存副本、互相覆盖（与 docs/27「罐不要跨 Dio 复用」同源）；③ `AppOrchestrator.switchSite` 在切站后调用 `SessionRegistry.reloadAll()`——否则**新**当前站点仍留着旧的作用域会话，又变成"两个罐指向同一目录"。**教训**：把单例改成多实例（无状态化）时，凡是"闭包捕获的可变状态"，都要逐处改成**运行时解析**；判断"是否同一个实例"用**显式标记**而不是 `identical` 一个 `late final` 字段。相关机制见 `docs/20`，跨站约定见 `docs/27`。

99. **索引与正文分表存储时，索引记录必须自带主键** — 症状：帖子缓存「写入成功」但管理页/过期清理/版本裁剪读到的索引恒为空（`listMeta` 静默跳过所有记录，`readMeta` 恒 null）。**根因**：`ThreadSnapshotMeta.toMap()` 序列化时漏了 `key`，读取侧 `tryFromMap` 又要求 `key` 非空；sembast 的 record key 在**外层**，值里不带主键，两处一拆开就对不上——全程无异常、无日志，只有列表为空。**修法**：`toMap` 显式写入 `'key': key`，并补 `toMap → tryFromMap` 往返单测（`test/thread_cache_test.dart`）。**教训**：分表存储时值必须**自描述**（主键写进值里），不要假设读方还能拿到 record key；这类"写进去/读不到"的 bug 只能靠序列化往返测试提前发现。
