# 设置分层与存储重构报告

> 状态：已实施（破坏性重构，不迁移旧设置项；落地方案见 `lib/core/settings/settings_repository.dart`、`lib/models/settings/`）。
> 注意：第 1~2 节描述的是**重构前**的存储现状，保留作为问题依据，不代表当前代码。
> 目标：把当前扁平的设置存储拆成 **应用设置 / 站点设置 / 账号设置（预留）** 三层，让作用域可判定、可检索、可迁移，并把「站点相关」的设置从应用设置里彻底移出去。
> 关联文档：`docs/04-状态管理.md`、`docs/27-跨站点会话与多用户.md`、`docs/07-经验教训.md`（#51 设置项存在不等于找得到、#52 分组按用户关心什么划分）

---

## 0. 结论先行

1. 当前设置**没有作用域模型**，只有「一个扁平 KV + 若干临时 per-site 存法」。同一个站点相关设置，可能分布在 5 种不同位置。
2. 真正的问题不是「键名不统一」，而是**读取方拿不到「这是哪个站点/哪个账号的设置」这个上下文**。所以现在只能在启动/切站时手工把值 push 到模块级变量里，漏一步就出错。
3. 建议引入 **`SettingsRepository`（同步内存快照 + 分作用域文档）**：
   - 应用设置：`AppSettings` 一份；
   - 站点设置：`SiteSettings` 每个 host 一份；
   - 账号设置：`AccountSettings` 每个 `host + uid` 一份（先留空）；
   - 站点派生数据（CDN、表情、作者资料）：`SiteState`，与用户设置分开存。
4. 所有读取方改为**按 host 拉取**，而不是在切站时 push：API 请求按 `baseUrl` 的 host 取、图片缓存按图片 URL 归属站点取、页面接管按路由里的 `site=`/当前站点取。这样站点切换不再需要「重载 per-site 配置」这一步。
5. 迁移采用「新库双读写 + 旧键保留一版」的方式，不一次性删除旧数据，保证可回滚。
6. UI 同步拆分：设置首页从「站点与网络」这种混合分组，改成 **应用设置 / 站点设置 / 账号设置 / 关于** 四个入口；站点设置页顶部固定站点选择器，所有项只对选中的站点生效。

## 1. 当前存储方案（事实梳理）

### 1.1 物理位置

| 位置 | 形态 | 内容 |
|---|---|---|
| `{appDataDir}/mtbbs.sembast` | sembast 主库 | 设置、站点、账号、历史、快照、预览缓存等 |
| `{appDataDir}/threads.sembast` | 独立 sembast | 帖子缓存，刻意隔离（docs/24） |
| `{appDataDir}/cookies/{host}/{account}` | 文件 | 各站点/账号 Cookie |
| `assets/config/*.json` | 只读资源 | 站点、工具栏、快捷键、缓存、常用语默认值 |

### 1.2 主库里的 Store

见 [database_helper_stores.dart](lib/core/utils/database_helper_stores.dart#L21-L55)：

| Store | Key | 用途 | 实际作用域 |
|---|---|---|---|
| `app_settings` | 任意字符串 | **所有扁平设置键** + `getMeta/setMeta` 的临时数据 | 混合 |
| `app_sites` | `sites` | `List<Site>` JSON | 应用（站点集合） |
| `app_accounts` | host | 该站账号列表 JSON | 账号 |
| `last_account` | host | 上次登录账号 | 账号运行时 |
| `credit_formula` | host | 积分公式 | 站点 |
| `shortcut_links` | host | 快捷链接列表 | 站点 |
| `toolbar_items` | `items` | 编辑器工具栏 | 应用 |
| `app_shortcuts` | `shortcuts` | 全局快捷键 | 应用 |
| `toolbar_shortcuts` | `tb_shortcuts` | 工具栏快捷键 | 应用 |
| `disabled_bbcode` | `disabled` | 禁用的 BBCode 标签 | 应用 |
| `image_history` | `history` | 图床上传历史 | 应用/账号待定 |
| `avatar_redirects` | 原始 URL | 头像重定向映射 | 站点派生数据 |
| `browse_records` / `search_history` / `editor_snapshots` / `preview_cache` | 各自 | 非设置数据 | — |

关键点：**`app_settings` 既是设置库，也是 `getMeta/setMeta` 的缓存库**（[database_helper_kv.dart](lib/core/utils/database_helper_kv.dart#L209-L226)）。因此 `site_cdn_map`、`smilie_data_{host}`、`emoji_usage_{host}`、`aboutAuthorProfile_{host}`、`defaultAccount_{host}` 这些「站点派生数据 / 站点状态」与真正的用户设置物理上混在一起。

### 1.3 值的编码方式

`setSetting` 统一写成 `{value: String}`（[database_helper_kv.dart](lib/core/utils/database_helper_kv.dart#L11-L21)）：

- int / double：存字符串，读时再 `int.tryParse` / `double.tryParse`；
- bool：绝大多数存 `'true'/'false'`，但 `autoFrequentTabs` 存 `'1'/'0'`（读取判 `!= '0'`）；
- enum：手工存 `name` 或 `index`（`themeMode` / `noticeBadgeMode` / `avatarSizeMode`）；
- 列表/Map：JSON 字符串。
- 没有 schema 版本、没有类型声明、没有迁移框架。

### 1.4 站点作用域的 5 种实现方式

这是当前最核心的结构问题。同一个「按站点隔离」的需求，代码里有 5 套写法：

| 方式 | 例子 | 读取方式 |
|---|---|---|
| A. 独立 Store，key = host | `credit_formula`、`shortcut_links`、`last_account`、`app_accounts` | `getCreditFormula(host)` |
| B. 扁平键后缀 `_{host}` | `defaultAccount_{host}`、`smilie_data_{host}`、`emoji_usage_{host}`、`aboutAuthorProfile_{host}` | 拼接字符串 |
| C. 塞进 `Site` JSON | `userAgent`、`avatarTemplate`、`forums`、`defaultForumOrder`、`name/baseUrl/loginPagePath` | `SiteStore.current` |
| D. 一张聚合 Map | `site_cdn_map`（`{host: {cdn, at}}`） | 整个 JSON 读出后按 host 查 |
| E. 内存里的 Map，写入时才拼 host | `_shortcutLinks[host]`、`AuthProvider._siteAccounts[host]` | 内存优先 |
| F. 全局单键（但语义是站点） | `simulateBrowserHeaders`、`interstitialAutoVerify`、`browserOnlyMode`、`browserFallbackPages`、`spaceSource`、`postMaxLength` | 直接读全局值 |

> 文档 `docs/04` 写的是「站点相关 key 命名：`{key}_{host}`」，但实际只有 B 类符合；A/C/D/E 都不符合。文档与实现已经漂移。

### 1.5 默认值与写入口

默认值至少分散在 4 处：

1. `assets/config/{sites,toolbar,shortcuts,cache,quick_replies}.json`；
2. `SettingsProvider` 字段初始值（如 `_fontSize = 16`、`_themeMode = system`）；
3. `DefaultConfig` 的解析兜底（如 `threadCacheConfig` 非法值回退 1 天 / 128 KiB）；
4. setter 里的 `clamp`（如 `setThreadCacheDays` 1~365、`setStaggerInterval` 20~300）。

结果是：改一个默认值，要同时找 2~3 个地方；文档里写的默认值也经常和代码不一致。

## 2. 当前设置项全量盘点

按当前设置页分组列出，并标注「真实作用域」与「当前存储位置」。

### 2.1 站点与网络

| 设置项 | 真实作用域 | 当前存储 | 问题 |
|---|---|---|---|
| 当前站点 | 应用（指针） | `currentSiteIndex` | 用 index 标识，站点排序/删除后不稳定 |

| 版块管理 | 站点 | `Site.forums` / `defaultForumOrder` | 存法 C |

| 管理快捷链接 | **站点** | `shortcut_links` | 存法 A + E |
| 通用错峰间隔 | 应用（可争议） | `staggerInterval` | 设备/网络属性；建议先留应用级，后续可加站点覆盖 |

### 2.3 阅读与渲染

全部为应用级：

`fontSize`、`codeBlockMaxLines`、`ratingMaxRows`、`disabledBbcodeTags`、`autoDetectUrls`、`noticeBadgeMode`、`noticeBadgeGroups`、`noticeCheckEnabled`、`shareImageMaxHeight`、`shareImageContentOnly`。

### 2.4 编辑与快捷键

| 设置项 | 真实作用域 | 当前存储 |
|---|---|---|

| **站点字数限制** | **站点** | 全局 `postMaxLength` | 
| 插入格式 / 快捷键 / 工具栏 / 常用语 | 应用 | `historyFormat_*` / `shortcuts` / `toolbarItems` / `quickReplies` |

> 「站点字数限制」名字已经说明它是站点级，但存储和读取都是全局。切换到字数上限不同的站点时，只能靠用户手动改。

### 2.5 存储与工具

| 设置项 | 真实作用域 | 当前存储 |
|---|---|---|
| 缓存管理（头像/表情/图片/勋章过期） | 应用 | `avatarCacheDays` 等 |
| 帖子缓存（TTL/开关/版本数/单帖上限） | 应用 | `threadCache*` |
| **表情管理** | **站点派生状态** | `smilie_data_{host}` / `emoji_usage_{host}` |
| MT 图床管理 | 应用/账号待定 | `image_history` |
| 浏览历史最大记录数 | 应用 | `historyMaxCount` |

### 2.6 页面接管

全部为全局单键，但语义是站点相关（用户明确指出的重点）：

`browserFallbackPages`（逐页关闭）、`browserOnlyMode`（整体逃生阀）。

### 2.7 MCP / 关于 / 开发者

- MCP：`mcpEnabled` / `mcpPort` / `mcpAllowRemote` / `mcpDisabledGroups` / `mcpTokens` → 应用级，安全敏感；
- 关于：`autoCheckUpdate` / `skippedUpdateVersion` → 应用级；
- 开发者：`developerMode`（应用级）、`acwForceWebview`（**站点级**，人机验证策略）；
- 窗口状态：`windowWidth/Height/X/Y/Maximized` → 应用/设备级，不属于业务设置。

### 2.8 粗扫结论

- `app_settings` 里约有 **60+ 个扁平键**，另有 **11 个专用 Store**；
- 真正属于「站点」的约 **12 项**，属于「账号」的目前只有账号列表 / 默认用户 / Cookie，账号级偏好基本为空；
- 站点相关项目前散落在 5 种存储方式里，没有统一入口。

## 3. 问题清单（按严重性）

### P0：会导致实际行为错误

1. **冷启动时积分公式可能读错站点**
   [settings_provider_persistence.dart](lib/providers/settings_provider_persistence.dart#L116-L135) 先用 `SiteStore.instance.host` 读公式，之后才根据 `currentSiteIndex` 切换站点。`SiteStore.init()` 默认 index 0，因此当前站点不是第 0 个时，启动后内存里的积分公式属于错误站点，直到用户手动切站才被 `AppOrchestrator.switchSite` 修正。

2. **站点切换有两条入口，行为不一致**
   - `SettingsSites.switchSite` 只写 index + notify；
   - `AppOrchestrator.switchSite` 额外做 `SiteStore.switchTo`、`reloadSiteConfig`、`auth.onSiteChanged`、`SessionRegistry.reloadAll`。
   任何新调用方如果用了前者，就会漏掉 per-site 重载。

3. **per-site 值靠「切站时 push」到模块变量**
   `simulateBrowserHeaders`、`browserFallbackPages`、`browserOnlyMode`、`spaceSource`、`interstitialAutoVerify`、`acwForceWebview` 都是模块级变量。只要某条路径没调用对应的 `apply*`，设置就会静默不生效。这类问题在跨站点场景（`site=` 参数）下更明显：请求的目标站点不是当前站点，但变量仍是当前站点的值。

4. **`currentSiteIndex` 用索引标识站点**
   删除站点、调整顺序、导入站点列表后索引会漂移；用 host 标识更稳定。

### P1：结构性问题，后续每加一个设置都会放大

5. **设置与派生缓存共用一个 Store / 命名空间**
   `site_cdn_map`、`smilie_data_*`、`aboutAuthorProfile_*` 与用户设置同库同前缀，无法做「只导出/清空设置」「只清缓存」这类操作。

6. **没有类型与 schema**
   全部存字符串，bool 还有两种编码；新增字段没有版本号，无法判断旧数据是否需要迁移。

7. **默认值分散在 4 处**
   见 1.5。站点级默认值还额外依赖 `DefaultConfig.shortcutLinksFor(host)`。

8. **`SettingsProvider` 是 7 个 part 的混合体**
   app/site/account 状态、写库、通知、业务 clamp 全在一层；UI 通过一个大 Provider 读取，改任何一项都会触发全局重建。

### P2：可用性问题

9. **设置页分组混杂**
   「站点与网络」里同时有站点、账号、应用三类；「页面接管」是全局入口但用户理解成站点行为；「站点字数限制」在编辑器组里但存的是全局值。

10. **搜索无作用域**
    搜索结果只显示分组名，不显示「应用 / 站点 / 账号」。将来同一个设置在不同站点有不同值时，搜索会让人误解改的是哪一份。

11. **文档与实现不一致**
    `docs/04` 声称统一 `{key}_{host}`，实际有 5 种存法（见 1.4）。

## 4. 目标模型

### 4.1 作用域判定规则

新增任何设置项，先回答这 4 个问题：

1. **换设备/重装应用后，这个值是否应该还在？**
   - 是 → 应用或账号；否（纯设备状态）→ 应用，但归入「本机状态」而非业务设置。
2. **切换到另一个站点，这个值应该变吗？**
   - 是 → **站点设置**。
3. **同一站点切换另一个账号，这个值应该变吗？**
   - 是 → **账号设置**。
4. **这是用户主动选择，还是系统自动识别的结果？**
   - 后者 → **站点派生状态（SiteState）**，不放进用户设置文档。

按这个规则，用户明确提到的项归类如下：

| 设置 | 归类 | 理由 |
|---|---|---|
| 默认启动页 = 导读 | **应用** | 整个 App 启动行为，与站点无关 |
| CDN | **站点派生状态** | 由站点模板自动识别，不是用户偏好 |
| 积分公式 | **站点设置** | 不同站点公式不同 |
| 表情 | **站点派生状态** | 表情包与使用频率按站点隔离 |
| 页面接管（逐页 + 整体降级） | **站点设置** | 不同站点对 App 页面支持不同 |
| 人机验证（自动处理 / 强制网页） | **站点设置** | 不同站点防护策略不同 |
| 是否携带 Referer/Accept | **站点设置** | 52pojie 等站点必须带 |
| 某账号设为站点默认账号 | **站点设置** | 是「站点选择用哪个身份读」，不是账号自身偏好 |
| 站点字数上限 | **站点设置** | Discuz 各站配置不同 |
| 个人空间数据源（移动/桌面） | **站点设置** | 模板差异 |
| 通用错峰间隔 | **应用**（可争议） | 设备与网络属性；如需按站可后续加覆盖 |

### 4.2 对象模型

```dart
class AppSettings {
  final int schemaVersion;
  final String currentSiteHost;        // 用 host，替代 currentSiteIndex

  final AppearanceSettings appearance; // 主题、纯黑、头像、图片宽度
  final ReadingSettings reading;       // 字号、代码块、评分、BBCode、链接识别
  final StartupSettings startup;       // 启动页、双击退出、首页区块、导读/消息 Tab
  final EditorSettings editor;         // 快照、迷你编辑器、工具栏、快捷键、常用语
  final StorageSettings storage;       // 图片缓存、帖子缓存
  final NoticeSettings notice;         // 未读徽标、检查开关、分组
  final ShareSettings share;           // 分享图
  final HistorySettings history;       // 历史条数、格式
  final AdvancedSettings advanced;     // 更新、开发者、MCP
  final WindowState window;            // 桌面窗口（可继续独立存）
}

class SiteSettings {
  final int schemaVersion;
  final String host;

  final SiteNetworkSettings network;   // referer、人机验证、强制网页
  final SitePageGateSettings pages;    // disabledPageIds、browserOnly
  final SiteContentSettings content;   // postMaxLength、spaceSource
  final SiteIdentitySettings identity; // defaultAccount
  final String creditFormula;
  final List<ManagedItem> shortcutLinks;
}

class AccountSettings {
  final int schemaVersion;
  final String host;
  final String uid;
  // 预留：自动签到、默认匿名、通知偏好、签名等账号级行为
}

class SiteState {                      // 派生数据，不是用户设置
  final String host;
  final CdnState? cdn;
  final EmojiState? emoji;
  final UserProfile? aboutAuthor;
}
```

说明：

- `Site`（名称、baseUrl、登录页、UA、头像模板、版块）**第一阶段仍留在 `app_sites`**。它已经是「一个站点一份」的聚合，强行并进 `SiteSettings` 会把 `SiteStore` / `SessionRegistry` / 路由全部牵动，收益小于风险。第二阶段可选合并。
- `SiteSettings.host` 与 `Site.host` 一致，通过 host 关联。
- `AccountSettings` 先建表但不落业务字段，避免以后再次改结构。

### 4.3 存储布局（推荐）

新增 4 个 Store，旧 Store 保留只读：

| Store | Key | Value | 说明 |
|---|---|---|---|
| `app_settings_v2` | `app` | `AppSettings` JSON | 一份应用设置文档 |
| `site_settings_v2` | host | `SiteSettings` JSON | 每个站点一份 |
| `account_settings_v2` | `{host}|{uid}` | `AccountSettings` JSON | 预留 |
| `site_state` | `{host}|{kind}` | JSON | `cdn` / `emoji` / `emoji_usage` / `about_author` |

为什么不继续用「扁平键 + 前缀」：

- 一份文档可以带 `schemaVersion`，迁移判断简单；
- 站点删除时可以整文档删除，不会留下 `defaultAccount_x`、`smilie_data_x` 之类的孤儿键；
- 导出/备份可以按作用域整份导出；
- 避免 `getMeta` 和设置继续混在一起。

> 备选方案：在原 `app_settings` 里用 `app.*` / `site.{host}.*` 命名空间。优点是改动小，缺点是类型与 schema 问题仍在，且 key 解析容易出错。本报告推荐新 Store 方案。

### 4.4 读取 API 与启动顺序

新增单例 `SettingsRepository`：

```dart
class SettingsRepository {
  static final SettingsRepository instance = ...;

  AppSettings get app;                       // 同步
  SiteSettings site(String host);            // 同步；未知 host 返回默认值
  AccountSettings account(String host, String uid);
  SiteState stateFor(String host);

  Future<void> loadAll();                    // 启动时一次加载
  Future<void> saveApp(AppSettings v);
  Future<void> saveSite(SiteSettings v);
  Future<void> saveAccount(AccountSettings v);
}
```

启动顺序调整为：

1. `DefaultConfig.load()`
2. `SettingsRepository.loadAll()`：先读 `app_sites` 得到站点列表，再读 app 文档 + 每个 host 的 site 文档
3. `SiteStore.init(sites: ..., currentHost: ...)`
4. `ApiService.init(...)`
5. 其余 Provider / SessionRegistry

这样所有早期模块都能同步拿到「某个 host 的设置」，不再需要在 main 里手工 `apply*`。

### 4.5 通知模型

- 第一阶段：`SettingsRepository` 继承 `ChangeNotifier`，任何作用域变化都 notify；`SettingsProvider` 变成薄壳，继续对 UI 暴露现有 getter/setter，避免一次性改完所有页面。
- 第三阶段（可选）：按作用域拆 `ValueListenable`，让「改站点 A 的 Referer」不重建主题、不重建首页。

## 5. 专项设计

### 5.1 Referer / 浏览器仿真头（站点级）

现状：

- `ApiService` 在创建 Dio 时读全局 `_simulateBrowserHeaders`，写入 `Referer/Accept`（[api_service.dart](lib/services/api_service.dart#L128-L145)）；
- 开关变化和切站时调用 `refreshBrowserHeaders()` 手工刷新；
- 图片缓存用 `browserHeadersEnabled()` 全局判断 + `refererForUrl(url)` 按图片 host 反查站点（[cache_utils.dart](lib/core/utils/cache_utils.dart#L60-L70)、[session_registry.dart](lib/core/app/session_registry.dart#L213-L227)）。

目标：

- 每个站点一份 `network.simulateBrowserHeaders`；
- API → 在 `onRequest` 拦截器里按 `options.baseUrl` 的 host 查询设置，决定是否加 Referer/Accept；
- 图片 → 先按图片 URL host 找到归属站点（`refererForUrl` 已有逻辑），再用该站点的开关；
- 删除 `_simulateBrowserHeaders` / `refreshBrowserHeaders()` / `browserHeadersEnabled()` 这套 push 机制。

注意：图片 host 可能是站点 CDN（`icdn.binmt.cc`），不等于站点 host。归属判定要同时覆盖 `Site.baseUrl` host 和 `SiteCdnStore` 已知 CDN host；找不到归属时回退当前站点。

### 5.2 页面接管（站点级 + 站点内逃生阀）

现状：

- `applyDisabledAppPages` / `applyBrowserOnlyMode` 模块变量（[app_page_gate.dart](lib/core/app/app_page_gate.dart#L55-L129)）；
- `appPageRedirect` 只读全局集合。

目标：

- `SiteSettings.pages.disabledPageIds` + `pages.browserOnly`；
- `appPageRedirect(location)` 先解析目标站点：
  - location 带 `site=<host>` → 用该 host；
  - 否则用当前站点 `SiteStore.instance.host`；
- 查该站点的页面接管配置；
- 删除 `applyDisabledAppPages` / `applyBrowserOnlyMode`，改为纯函数 + 仓库查询（便于单测）。

`browserOnlyMode` 建议也改为**站点级**：用户在 A 站被验证卡住时只降级 A 站，B 站仍用 App 页面。设置页文案改为「本站点全部改用内置浏览器」。设置路由仍然豁免，保证能改回来。

### 5.3 人机验证（站点级）

现状：

- `VerificationGate.instance.isEnabled` 全局回调（[main.dart](lib/main.dart#L116-L124)）；
- `JsChallengeSolver.instance.skipLocalSolve` 全局回调；
- `acwForceWebview` 在开发者选项里，但语义是站点级。

目标：

- 回调改为按请求上下文取 host：`VerificationGate` 的 `InterstitialContext` 已带 `baseUrl`，用它反查 host；
- `skipLocalSolve` 同样按请求 host；
- 开发者选项中的「改用网页完成」移到站点设置（或保留在开发者页但明确「仅对当前站点」）。

### 5.4 默认用户（站点级）

现状：

- `defaultAccount_{host}` 存在 `app_settings`；
- `SessionRegistry` 初始化时异步读入 `_HostInfo.defaultAccount`。

目标：

- 存入 `SiteSettings.identity.defaultAccount`；
- `SessionRegistry` 初始化时直接同步读 `SettingsRepository.site(host).identity.defaultAccount`，去掉 `_readDefaultAccount` 的异步磁盘读取；
- `setDefaultAccount` 写入 site 文档后 `refreshHost(host)`；
- 账号列表（`app_accounts`）和上次登录（`last_account`）仍留在账号域，不并入站点设置。

### 5.5 CDN / 表情（站点派生状态）

用户把它们归为站点设置是合理的，但要区分「用户可编辑的设置」和「系统识别的状态」：

- CDN：自动识别，不应出现在「可编辑设置」列表里，只在站点设置页显示「已识别 / 未识别 + 刷新」；
- 表情：表情包按站点抓取，使用频率按站点累计；管理页只提供「刷新 / 清空」；
- 两者都应从 `app_settings` 的 `getMeta` 迁到 `site_state`，避免继续和用户设置混存；
- 不放进 `SiteSettings` 文档，避免每次保存设置都重写大体积表情数据。

### 5.6 积分公式 / 快捷链接（站点设置）

- `creditFormula`：从 `credit_formula` store 迁入 `SiteSettings.integrations.creditFormula`；
- `shortcutLinks`：从 `shortcut_links` store 迁入 `SiteSettings.ui.shortcutLinks`；
- 读取方不再缓存「当前站点的公式」，而是每次按 host 取，顺带修掉 3.1 的冷启动 bug；
- 写入必须显式带 host，杜绝「对话框打开期间切站导致写错站点」。

### 5.7 站点身份（`Site` 对象）

第一阶段保持现状：

- `name` / `baseUrl` / `loginPagePath` / `userAgent` / `avatarTemplate` / `forums` / `defaultForumOrder` 继续存在 `app_sites`；
- `SiteSettings` 只承载「行为设置」，不重复存身份字段；
- 站点删除时，同步删除 `site_settings_v2[host]` 与 `site_state[host|*]`。

第二阶段可选：把 `logo/主题色/首页区块是否按站点` 等未来字段逐步并入 `SiteSettings`，但不在本次范围。

### 7.3 旧全局值的迁移策略

`simulateBrowserHeaders`、`interstitialAutoVerify`、`acwForceWebview`、`browserFallbackPages`、`browserOnlyMode`、`spaceSource`、`postMaxLength` 之前是全局值。迁移时有两种选择：

- **推荐：复制到所有已配置站点**。这样升级后行为完全不变；之后用户改某个站点才产生差异。
- 备选：只复制到当前站点，其它站点取默认值。会让老用户升级后其它站点行为变化，不建议。

迁移需要幂等：以 `settingsSchemaVersion` 或 `site_settings_v2` 是否存在为准，只执行一次；旧键保留到第 5 阶段再删。

### 7.4 站点删除 / 新增

- 新增站点：写入默认 `SiteSettings`（从默认值生成），不复制其它站点；
- 删除站点：删除 `site_settings_v2[host]`、`site_state[host|*]`、`credit_formula[host]`、`shortcut_links[host]`、`defaultAccount_{host}` 等所有该 host 的遗留键；
- 站点改 baseUrl（host 变化）：需要把 site 文档从旧 host 迁到新 host。这是当前也存在的隐患（`SessionRegistry.reloadAll` 只重建会话，不迁设置）。

## 8. 风险与验证

### 8.1 主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 启动顺序 | 早期模块（ApiService、router）需要同步读设置 | `SettingsRepository.loadAll()` 在任何消费者之前完成；普通 getter 必须同步 |
| 跨站解析 | 请求/路由/图片 URL 的目标 host 解析不一致 | 统一一个 `resolveSettingsHost(...)` 工具，禁止各处自己拼 |
| CDN host ≠ 站点 host | 图片 Referer 归属判断 | 复用并扩展 `refererForUrl`，覆盖 baseUrl + CDN host |
| 旧全局值语义 | 复制到所有站点还是当前站点 | 按 7.3 推荐复制到所有站点 |
| 回滚 | 旧版本不读新 Store | 旧键保留一版；关键开关在过渡期可双写 |
| 通知风暴 | 一个大 Provider 触发全 App 重建 | 第一阶段维持现状；第三阶段按作用域拆 |
| 设置搜索遗漏 | 新分组后搜索页找不到 | 继续用 `settings_groups.dart` 单一清单（docs/07 #51） |
| 站点删除残留 | 孤儿 site 文档 / 缓存 | 删除站点时级联清理 |
| 迁移不幂等 | 重复迁移覆盖用户改动 | schemaVersion + 只迁移一次 |

### 8.2 验证清单

- 单测：
  - 作用域判定与默认值（未知 host 回退）；
  - 迁移幂等（连续跑两次结果一致）；
  - `currentSiteHost` 回退（站点被删除）；
  - 站点删除级联清理；
  - Referer 开关按站点生效（含 CDN host 归属）；
  - 页面接管按 `site=` 参数生效；
  - 积分公式冷启动读对站点。
- 现有测试回归：
  - `test/app_page_gate_test.dart`；
  - `test/thread_cache_test.dart`；
  - 设置搜索相关测试（如有）。
- 手工矩阵：
  - 两个站点，分别设置不同 Referer / 页面接管 / 默认用户 / 字数上限；
  - 切换站点后确认请求头、页面跳转、编辑器字数限制分别变化；
  - 跨站打开帖子（`site=`），确认使用目标站点设置而不是当前站点设置；
  - 删除站点后确认无残留设置 / 缓存；
  - 冷启动直接进入非第 0 个站点，确认积分公式正确。
