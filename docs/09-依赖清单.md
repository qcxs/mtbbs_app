# 依赖清单与行为约定

只记录**核心理念、行为关键点与大忌**。完整用法读源码 / pub.dev。

## 一、核心理念：优先用成熟方案

依赖不是"第三方代码"，而是**项目的一部分**——成熟依赖早已替我们踩平了跨平台、性能、边界情况这些坑。

- **自己实现的代价被低估**：手写代码只覆盖"设计时想到的路径"，而成熟依赖经受了大量真实场景验证。跨平台差异（Windows 文件锁、Android 压缩、iOS 手势冲突）、性能细节（内存缓存、并发、LRU）、意外情况（损坏文件、断网、并发读写），每一项自己实现都是长期的 bug 源。
- **实例**：图片查看器曾手写两版（手势冲突、缩放动画、双指/单指切换全是坑），切到 `photo_view` 后零代码量、表现完美（见经验教训）。
- **何时用依赖**：涉及平台差异、手势/渲染、网络、存储、安全等系统级能力，或需要稳定生命周期管理时，一律选成熟依赖。
- **何时自己写**：论坛特有、无成熟包可用的纯逻辑（如 BBCode 解析、Discuz HTML 解析），才手写。

## 三、大忌：不要臆断依赖行为

> 凭旧版本记忆或直觉判断"看不见的机制"（自动清理、自动重试、隐式转换），是最大的坑。

### 案例：误以为 flutter_cache_manager 没有自动清理

**误以为**：缓存过期后不会自动删除，需要自己扫描目录清理。

**真相**（3.4.1 源码 `CacheStore._cleanupCache`）：
- **内置自动清理**：每次缓存磁盘读取后 10 秒自动调度一次
- 判定依据是 **`touched`（最后使用时间）**：删除超过 `stalePeriod` 未使用过的对象
- 文件 + 元数据 + 内存缓存**同步删除**，无孤儿记录；另按 `maxNrOfCacheObjects` 做 LRU 淘汰

**差点手写 mtime 目录扫描的错误后果**：
- mtime（≈下载时间）≠ 最后使用时间 → **误删"过期天数内仍在看的图片"**（库每次命中都会更新 `touched`）
- 直接删文件不同步元数据 → 孤儿记录，状态不一致
- 启动时全目录递归扫描 + stat，与启动争抢 I/O；Windows 上删除被打开的文件还会抛异常

**正确做法**：直接用内置机制，`stalePeriod` 即"过期天数内未使用"的判定区间；`validTill` 决定访问时是否刷新重下。

### 通用规则

用任何依赖前，**先读源码 / 文档确认行为**，尤其涉及清理、重试、缓存、编码转换这类隐式机制。改依赖版本前读 CHANGELOG，注意行为变更（本案例的内置清理就是较新版本才有的）。

## 四、版本管理

- 实际锁定版本以 `pubspec.lock` 为准（当前 flutter_cache_manager 解析为 3.4.1）
- 升级：`flutter pub outdated` 查看 → 读 CHANGELOG → 确认行为差异后手动升级；不无脑 `--major-versions`
